# The Semester UI constitution

> Owner, version, last and next review, status, supersedes and related decisions: [`SEMESTER-OPERATING-SYSTEM.md`](../../SEMESTER-OPERATING-SYSTEM.md).

Semester has a lot of capability: sixty-three destinations, eighty-four
screens, and a component directory of more than two hundred files. The main
design risk is not a missing feature. It is that a student experiences all of
this as a collection of separate tools instead of one system. This document
sets the rules that keep it one system. It also says, for each rule, **what
enforces it today** and **what is still owed**.

It is written against the code as it is. Most of what a generic design-system
plan asks for already exists here under another name: a token system, a shared
screen frame, a source-label vocabulary, and a set of accessibility tests. Many
of those were built to fix a bug, and the docblocks record which one. A plan
that rebuilt them from scratch would throw that history away. So this
constitution maps the plan onto what exists. It builds only what was missing,
and it lists separately the changes that alter what every student sees, which
need screenshots and a yes before anyone makes them.

| | |
|---|---|
| **Applies to** | Every screen, component and stylesheet under `app/src/`, every contributor, and every agent session |
| **Inventory** | [SCREEN-AUDIT.md](SCREEN-AUDIT.md), generated by `npm run audit:screens -- --write` |
| **Navigation areas** | `app/src/lib/navareas.ts`, held by `lib/navareas.test.ts` |
| **Frame guard** | `app/src/pageframe.test.ts` |
| **Token source** | `app/src/lib/look.ts` → CSS custom properties on `:root` |
| **Older detail** | [DESIGN-SYSTEM-IMPROVEMENTS.md](../DESIGN-SYSTEM-IMPROVEMENTS.md) holds the component contracts. This document does not repeat them. |

## 1. The ten rules

These are product rules, not suggestions. Where a rule has a guard, breaking
the rule fails CI. Where it has none yet, the PR checklist
(`.github/pull_request_template.md`) asks the question, and §11 records the
gap.

| # | Rule | Held today by | Still owed |
|---|---|---|---|
| 1 | Every screen uses the same application shell. | `App.tsx` draws the header, tab bar, skip link and `<main>` once for all layouts. `pageframe.test.ts` requires every screen module to render `<Page>`, or to appear on a list of named exceptions that can only get shorter. | There are two frames, `Page` and `SettingsPage`. Nine modules are frameless (§11). |
| 2 | Every page uses the approved header pattern. | The header's `<h1>` and kicker come from `useHeader()` in `App.tsx`, and a screen cannot draw its own. `Page` owns the purpose sentence (`blurb`) and the screen's own action row (`actions`). `Page` draws the registry sentence by default (§12, decision 5), so 66 of 84 screens now say what they are for. The rest are frameless, nested or opted out. |
| 3 | Every page has one dominant primary action. | `ActionButton` / `.btn-primary`. The rule that a view has one metal CTA is in `look.ts`. | There is no guard. There are two primary styles, `.btn-primary` and `.portal-primary` (§11). |
| 4 | Every action looks and behaves the same everywhere. | `ActionButton` (`HEIGHT = 46`), `.bare`, `.tappable`. `Undone` is the one undo. `TypeToConfirm` is the one irreversible confirm. | The same `.portal-*` fork as rule 3. |
| 5 | Every object uses one consistent detail pattern. | Deadlines (`item`), events (`event`) and courses (`course`) each have one detail screen. | There is no shared Action object sheet yet (§6). |
| 6 | Every screen has loading, empty, error and restricted-access states. | Route loading is the skeleton in `App.tsx`. `ui.tsx` has `EmptyState`. `Boundary.tsx` has `ScreenTrouble`. `Trouble.tsx` and `Notice` cover errors. | Only 13 modules use `EmptyState`. There is no shared permission-state component. |
| 7 | Every screen works with keyboard, touch, screen reader, zoom and small screens. | `a11y/*.test.ts`, `styles/taps.test.ts`, `styles/textscale.test.ts`, `scripts/labels.mjs`, `npm run sweep:targets` (§8). | Responsive review is by screenshot (`.claude/skills/run`), not a gate. |
| 8 | Every source of information is visibly identified. | `lib/source.ts` defines five labels, matched to the database. `SourceBadge` shows them. `NotOfficial` is the prose form. `IntelligenceDisclosure` is the AI receipt. Only 3 screen modules show a source label. AI-assisted and external content now share the badge (§7). |
| 9 | Every screen uses approved primitives. | `ui.tsx`, `Page`, `Surface`, `Popover`, `a11y/modal.ts`, and the per-file style budget (`styles/rules.ts`, `budget.ts`, `npm run lint`). | 5 colour literals remain in 4 screen modules. The `.portal-*` system is outside the tokens. |
| 10 | No new one-off CSS, colour, button, card, modal, tab or icon pattern without review. | `npm run lint:styles` rejects new literals on the type, leading and dim scales per file. The PR checklist asks the question. | There is no stylesheet lint for new hex values or px radii in `styles/` (DS-8 in the older doc). |

## 2. Information architecture: the navigation areas

Top-level navigation is organised around how a student thinks, not around
every capability the app has. Each area answers one question.

| Area | The student's question | Front door | Primary action | Destinations |
|---|---|---|---|---:|
| **Today** | What do I need to do now? | `home` (Today) | Complete the next action | 3 |
| **Plan** | What is coming up, and how do I organise it? | `calendar` | Add or schedule something | 12 |
| **Learn** | How do I get this academic work done? | `study` | Start a study session | 22 |
| **Help** | Who or what can help me? | `support` | Connect to a service | 5 |
| **Campus** | What is happening, and where do I go? | `maps` | Get directions or save an event | 11 |
| **Progress** | How am I doing? | `me` (Progress) | Review the recommended next step | 3 |
| **You** | What are my settings and preferences? | `settings` | Change a setting | 7 |

`lib/navareas.ts` is the source of truth. `navareas.test.ts` checks four things:

- every destination has exactly one area;
- the map names nothing that is not a destination;
- each area's front door sits inside that area;
- there are no more than seven areas.

To place a screen whose area is debatable, ask what question the student is
asking when they open it, not what the screen contains. For example,
Registration is Plan even though it lists courses.

**How the areas relate to what already exists.** The registry already files
every screen two ways:

- `group`, the eight launcher shelves: Semester, Courses, Study, Make, Campus,
  Life, Beyond, Data.
- `taskTags`, the nine intentions under Progress → By task.

The areas are a third reading, and the one the navigation is now drawn from.
They are a separate map rather than a field in `lib/nav.ts`, so that the map
does not conflict with every open branch. There are also two near-namesakes,
which are different things. `lib/journeys.ts` holds six guided routes, and a
screen can be on several of them. `lib/journey-areas.ts` records the 26
expansion areas from a product brief.

**The launcher is drawn by area (decision 1).** Three views use the seven
areas as their headings: the grid button's sheet (`AllApps`), the workspace's
apps panel, and the workspace directory's filter chips and row labels. Each
student's drag order still holds inside an area. The shelves are still what
the shelf navigation and the springboard draw, because those are single rows
held to 5–8 screens each, and the areas are not sized for that.

**The default bottom bar is one front door per area (decision 2):** Today,
Calendar, Study, Support and Progress, which are Today, Plan, Learn, Help and
Progress. Courses gave way to Support. This affects fresh installs only,
because the bar is saved state.

**Progressive disclosure.** The top level holds only the area front doors. The
second level holds the tools inside each area. The third level holds advanced
controls, analytics, export and preferences. Learn holds 22 destinations, and
that is the clearest consolidation target in the app (§10, Phase 3): one
Study Studio front door with the specialist tools behind it, instead of 22
peers.

## 3. The shell

Every screen renders inside one structure. The plan's names map onto the code
like this.

| The plan calls it | In this codebase | Rule |
|---|---|---|
| Global header | `Header` in `App.tsx`. On the workspace layout, `components/desk/TopBar.tsx`. | The layout of the header never changes by area. The content changes. The shell does not. |
| Context bar | The header **kicker**, from `src/headers.ts` `headOf()`: the course code, the date, the load. The course link beside it goes up one level (`lib/parent.ts`). | The kicker says where you are and what you are looking at. A screen that needs a new context line changes `headOf`, not its own markup. |
| Page title | The header's `<h1>`, from `useHeader()` | A screen never draws a second heading. `Page` takes no `title`, and `Clocks.tsx` records why. |
| One-sentence purpose | `<Page blurb=…>` | Every destination has this sentence in `lib/nav.ts` as `blurb`. The screen should show it. |
| Primary action | `<Page actions=…>` with one `ActionButton` | This is one primary. Secondary actions are `.btn` or `.bare`. |
| Main content | `Page` children, inside `ScrollArea`'s `<main id="main">` | The gutter is `--page-pad`, set per layout. It is never a literal. |
| Contextual side panel | The workspace layout's columns (`components/desk/`) and `Popover` / sheets on a phone | This panel is never needed to finish the primary task. |
| Persistent command access | The header's search icon → `Command.tsx` (`lib/find.ts`), `/` from anywhere, and `+` → `QuickAdd.tsx` | There is one search. `Page` owns no search field, and `Page.tsx` records why. |
| Skip link and landmarks | `SkipLink` in `App.tsx`, checked by `a11y/landmarks.test.ts` | These are drawn once, in both layouts. |

**Breakpoints.** There are three: `TABLET_AT = 760`, `DESKTOP_AT = 1180`, and
`TALL_AT = 600` for height, all in `lib/media.ts`. New CSS uses only these.
There are 19 older breakpoints, and each is migrated only when its file is
touched for another reason.

## 4. Tokens

The token system is `lib/look.ts`. `App.tsx` writes it onto `:root`. It is
more capable than the plan's example values, because **density, text size,
line height, reading width and motion are student settings.** A literal pixel
value ignores all of them.

| Plan token | Use here | Note |
|---|---|---|
| `--space-1…7` (4–48px) | `--sp-1…7` = 2, 4, 6, 8, 10, 12, 16 px × `--density` | Larger gaps are multiples of `--sp-7`. The scale is not renamed: 2,500+ uses depend on it. |
| `--radius-sm/md/lg` | `--r-sm`, `--r-md`, `--r-lg`, resolved per ground | Never a literal radius. `features.css` still has some (DS-2). |
| `--tap-min: 44px` | `max(100%, 44px)` on targets, checked by `styles/taps.test.ts` | The *target* grows to 44px while the drawing stays the same size. |
| `--content-max`, `--reading-max` | `--reading-width` (a student setting) and `className="prose"` on `Page` | |
| Type scale | `--type-*` × `--text-scale`. New components use six semantic steps: `xs` metadata, `sm` secondary, `md` body/row, `lg` card title, `display-sm` section, `display-lg` screen. | The half-steps are aliased, not deleted (DS-4). |
| Colour and status | The `--app-*` tokens, including `-warn`, `-warn-line`, `-warn-wash`, `-passing` and the accent family | A new colour token needs a `lib/contrast.test.ts` row across all 13 grounds. See `CLAUDE.md` §Contrast. |
| Motion | `--ease`, plus `data-calm` (`device`, `still`, `calm`) | Reduced motion is a setting as well as a media query. Checked by `a11y/motion.test.ts` and `a11y/calm.test.ts`. |
| Focus | The ring checked by `a11y/focus.test.ts` | |

Dark and light are **grounds**, not a media query. Never add
`prefers-color-scheme` CSS.

## 6. Visual language and object patterns

**Cards mean one thing:** a distinct object, decision or action. Reading,
instructions and simple lists are flat sections. Editing happens in a sheet so
that you keep your place. Multi-step work gets a full screen. Do not nest a
card in a card. Do not wrap a paragraph in a card to decorate it. Card anatomy
is always the same: status or category, title, one line of context, a
metadata row, the primary action, and an optional overflow menu.

**Colour is sparse and always means the same thing.**

| Colour | Meaning |
|---|---|
| Accent | The primary action or the selected state |
| Course colour | Course identity only, always with the course code as text |
| `--app-passing` | Confirmed, done, on track |
| `--app-warn*` | Needs attention, estimated, needs review |
| Red / urgent | Blocked, error, deadline at risk |
| Neutral / dim | Information, system state, external |

Colour is never the only signal (`a11y/tellings.test.ts`). An estimate or a
doubtful figure is styled to draw the eye, *more* than an official one
(`wantsAttention` in `lib/source.ts`). A student is most likely to over-trust
exactly those.

**Type communicates hierarchy, not personality.** Use the six semantic steps
in §4.

**Buttons.** There is one primary per page or task region, and at most two
visible secondary actions beside it. Labels start with a verb and name the
object: "Book tutoring", "Start a study session". Avoid a bare "Submit" or
"Manage". Destructive actions never use primary styling, and they confirm
through `TypeToConfirm`. External actions show that they leave Semester. An
icon-only button needs an accessible name (`scripts/labels.mjs`).

**The three layers.** Every complex task shows information in three layers:

1. What matters now: one summary and one action.
2. Why: the deadline, the course, the source, the impact.
3. Details: policies, data, alternatives, history.

These layers go behind a `Fold` or a sheet. They are never shown all at once.

**The Action object (owed).** A task can come from an LMS deadline, a personal
reminder, an advising follow-up, a financial-aid requirement or a referral.
Whatever its origin, it should open the same detail sheet, with these parts:

- title
- why it matters
- timing
- course or service
- source and freshness
- status
- next step
- materials
- how to get help
- history

`lib/actions.ts`'s `Explanation` shape (see the older doc, §4.3) is the start
of this. The sheet itself is Phase 2.

**Permission state (owed).** It says four things: what is unavailable, why,
who controls access, and what the student can do. It replaces blank panels and
"Something went wrong".

## 7. Trust and source language

Semester mixes records the institution checked, imported feeds, what the
student typed, estimates it worked out itself, and AI answers. A student has
to be able to tell these apart **at the point of decision**, not in settings
or on hover.

| Kind | Where it is today | Words shown |
|---|---|---|
| Official | `SourceBadge label="institution_verified"` | Institution verified |
| Synced / imported | `imported` | Imported |
| Student-created | `student_entered` | Student entered |
| Worked out by Semester | `estimated` | Estimated |
| Doubtful | `needs_review` | Needs review |
| AI-assisted | `SourceBadge label="ai_assisted"`, at the head of every `IntelligenceDisclosure` | AI-assisted |
| External | `SourceBadge label="external"`, added when an answer drew on the web | External |
| Not official, as prose | `NotOfficial` | "This is not official — confirm with your compliance office." |
| Freshness | `freshnessLine()` | "Updated 3 days ago". It never says "Live", and it says nothing when the time is unknown. |

The five `SourceLabel` values match the database's check constraint, and
`source.test.ts` fails if they drift. **Do not add AI-assisted or external to
that union.** It would break the database contract. The display is unified
instead (decision 3). `TRUST_KINDS` in `lib/source.ts` is the five plus
`ai_assisted` and `external`, for display only, and `SourceBadge` draws all
seven. An AI answer is styled to be noticed, like an estimate.

are already student settings (Settings → Look and Navigation). What is owed is
not more settings. It is making sure every screen responds to the ones that
exist. That is why a literal `px` is a finding.

## 9. The screen quality contract

A screen is not finished because it looks better. It is finished when every
box is checked. The PR template carries this list.

- [ ] It renders inside `<Page>` (or is on `FRAMELESS` with a reason).
- [ ] The header name comes from the registry. There is a one-sentence
  `blurb`.
- [ ] It has exactly one primary action.
- [ ] It uses only the components in §5 and the tokens in §4, with no new
  literals.
- [ ] It has loading, empty, error and permission states.
- [ ] It shows source and freshness wherever a decision depends on outside
  data.
- [ ] It has screenshots at 390px and 1280px, on one dark and one light
  ground.
- [ ] It works with keyboard only and with a screen reader, and the §8 guards
  are green.
- [ ] It reflows at 320px and at 200% zoom.
- [ ] It has a clear way back, and its context is kept (`lib/parent.ts`).
- [ ] Advanced controls stay behind a fold, a sheet or overflow until they are
  needed.
- [ ] It records view, primary action, completion and error events, if the
  screen is instrumented (see `ANALYTICS.md`).

### Scoring

Each criterion is scored 0, 1 or 2, for a total out of 20.

| Criterion | 0 | 1 | 2 | Scored by |
|---|---|---|---|---|
| Shell / frame | none | the second frame | `Page` | `audit:screens` |
| Purpose | none | — | `blurb` | `audit:screens` |
| Colour and tokens | 4 or more literals | 1–3 | none | `audit:screens` |
| Action hierarchy | 5 or more primaries | none, or 3–4 | 1–2 | `audit:screens` |
| Hand-styling | more than 8 inline styles per 100 lines | ≤8 | ≤3 | `audit:screens` |
| Responsive | desktop only | partial | intentional at all widths | person |
| Accessibility | untested | basic | verified | person |
| States | missing | partial | all four | person |
| Navigation clarity | confusing | mixed | clear | person |
| Content clarity | jargon | mixed | plain | person |

The bands for the full 20 are 16–20 system-ready, 11–15 targeted migration,
and 0–10 redesign before new features. `SCREEN-AUDIT.md` scores the
automatable half out of 10 and uses the same proportions: 9–10, 6–8 and 0–5.

## 11. Known debt, measured

From [SCREEN-AUDIT.md](SCREEN-AUDIT.md) at the time of writing. Regenerate the
file rather than editing these figures.

- **Two frames.** 61 modules use `Page` and 8 use `SettingsPage`. Converging
  them means `SettingsPage` rendering `Page` inside it, with its highlight
  behaviour kept.
- **Nine frameless modules.** Six have a current reason. For three of them,
  `Gap`, `Drill` and `Slides`, the stated reason ("the frame's search box")
  no longer holds: `Page` has had no search box since the search moved to the
  header. These should try `<Page wide bottom={0}>` next, with screenshots.
- **Purpose sentences.** Resolved by decision 5. 66 of 84 screens show one:
  21 their own, and 45 the registry's through `PagePurpose`. The 18 without
  one are frameless, nested (a course or a deadline) or Today.
- **A second primary-button style.** `.portal-primary` and the `.portal-*`
  family in `styles/features.css` are used by 2 screen modules (`Study`,
  `Courses`) and 11 components: the course hub, the study studio, the
  registration portal and day, the graduation simulator, the campus directory,
  the study journal and the toolkit panels. The audit counts screen modules
  only, so it understates this. Migrate the family to `ActionButton` /
  `.btn-primary`, together with DS-1 and DS-2.
- **Trust labels.** 5 screen modules show a source label. Registration, the
  degree and grades, the screens where a student decides something on the
  strength of a figure, now carry the one badge (`SourceBadge`): Student
  entered for what was typed or confirmed, Estimated for what is worked out
  from it. The degree screen said the same thing with the status chips'
  "Yours" and "Needs confirmation", a second vocabulary for one fact; it no
  longer does. `lib/status.ts` still words provenance through `lib/where.ts`
  ("Yours", "Made here"), so two provenance vocabularies remain in the code —
  converging them is the next step, and it touches every `where` caller.
- **Empty states.** 13 modules use `EmptyState`. The others either hold no
  list or write their own.

## 12. Decisions: all five signed off and built

The student approved all five. Each one is covered by tests and was checked in
the running app, at 420px and 1280px, with no page errors.

| # | Decision | Where | Guard |
|---|---|---|---|
| 1 | The launcher is drawn by area, not shelf | `lib/apps.ts` `appSections`, `AllApps`, `AppsPanel`, `lib/desk.ts` `categories`/`chipsFor`/`narrowApps`, `screens/Directory.tsx`, `desk/TopBar.tsx` | `apps.test.ts` checks that every app appears exactly once, in area order, and keeps the drag order. `desk.test.ts` checks the chips are areas. |
| 2 | Help is in the default bottom bar: Today, Calendar, Study, Support, Progress | `lib/tabbar.ts` `DEFAULT_TABS`, `state/shape.ts` `ROOTS` | `tabbar.test.ts`, and `navareas.test.ts`, which checks one front door per area |
| 3 | One trust badge, including AI-assisted and External | `lib/source.ts` `TRUST_KINDS`, `SourceBadge`, `intelligence/Disclosure.tsx` | `source.test.ts` checks the stored five are unchanged. `Disclosure.test.tsx` |
| 4 | One field for search, ask and add | `components/Command.tsx`, `lib/intent.ts`, `QuickAdd.tsx`, `desk/TopBar.tsx` | `intent.test.ts` checks that only explicit verbs count as an add, and that a screen's own name stays a search |
| 5 | Every screen shows its registry sentence by default | `components/Page.tsx` `PagePurpose`, `App.tsx` `CurrentScreen` | `pagepurpose.test.tsx`, shown to fail when the default is reverted |

**What was deliberately kept.** The header's `+` and the assistant button
stay as shortcuts. They open the same capture box and the same assistant as
the field's ADD and ASK, so neither is a separate system. The Action Center
stays too: it is Today's list of what to act on, not a way to enter
something. The shelves stay in
the shelf navigation and the springboard (see §2). The keyboard sheet still
describes `/` as "Search everything", because `onframe.test.ts` holds that
entry to wording with no "or".
