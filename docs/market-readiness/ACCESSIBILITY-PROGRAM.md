# Accessibility program

## Commitment and status

Semester targets WCAG 2.2 AA and equitable task completion across keyboard, screen reader, zoom/reflow, reduced motion, contrast and mobile use. Current evidence is automated and self-assessed; it is not a formal ACR or independent conformance claim.

## Pilot gate

Before each pilot, a qualified reviewer tests the exact student and administrator golden paths at 320 CSS px and 200% zoom, keyboard-only, and with the target screen-reader/browser combinations. The report records failures, severity, owner, workaround, remediation and retest. A critical blocker is a no-go.

## Product requirements

Semantic structure and landmarks; visible focus; logical order; skip links; operable dialogs/menus; labelled fields and errors; non-color status; 44×44 touch targets where practical; announcements for dynamic state; accessible documents/media/captions; plain language; no time/animation barrier; meaningful empty/loading/error/recovery states.

## Support and accommodation

Every user-facing surface links to barrier reporting. Support acknowledges the issue, captures the blocked task and assistive setup without unnecessary sensitive information, provides a safe equivalent path, escalates urgent academic-deadline barriers, and records remediation. The institution retains its accommodation obligations; Semester must not infer disability or decide eligibility.

## ACR/VPAT work plan

1. freeze the evaluated version and scope;
2. complete manual representative-flow and component review;
3. remediate critical/high findings and retest;
4. map evidence to the current VPAT edition with qualified review;
5. publish an accurate scope/date/limitations statement;
6. review at least annually and after material UI changes.
