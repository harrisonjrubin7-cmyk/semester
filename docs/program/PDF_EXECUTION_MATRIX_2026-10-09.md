## Continuous workflow compatibility note

The Registration Readiness registry models a refreshable aggregate across evaluation generations, not one never-ending command. Its exact graph is:

- `requested → evaluating`;
- `evaluating → ready | blocked | needs_review | unknown | stale`;
- `ready | blocked → evaluating` for a later refresh;
- `needs_review | unknown | stale → reconciling` before retry;
- `reconciling → evaluating` only when the reconciliation task is resolved and a new generation begins.

That aggregate is legitimately continuous because a later, newer projection can refresh an earlier result. The per-command completion invariant is separate: `ready`, `blocked`, `needs_review`, `unknown`, and `stale` are the declared `cycle_outcomes` and issue completed receipts; `requested`, `evaluating`, and `reconciling` remain pending. The validator requires every continuous state to reach a known cycle outcome, rejects any non-outcome cycle, and still rejects missing transition entries, valid-state dead ends, unknown targets and unreachable states. The direct `evaluating → reconciling` edge was removed so a new generation cannot start without first recording a completed outcome. The focused regression binds the full registry graph and cycle outcomes to the institution runtime definition, so `continuous: true` cannot hide a non-terminating request path.
