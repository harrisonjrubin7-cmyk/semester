AC-03 was your core cross-tenant test. The new complete suite adds these other nine controls:
Control ASVS area pgTAP assertion behavior
C02 V8 Authorization A student cannot insert a record with another tenant’s tenant_id
C03 V8 Authorization A student cannot self-insert role grants or take over owner_id
C04 V8 Authorization A direct privileged RPC cannot return a foreign resource
C05 V8 Authorization Views, derived data, and exports do not leak a foreign tenant’s record
C06 V8 Authorization A student cannot enumerate private storage metadata for a foreign tenant
C07 V8 Authorization Suspended or revoked users cannot access protected records
C08 V8 Authorization Expired staff grants do not authorize access
C09 V8 Authorization Privileged/RPC functions have deliberately restricted execution roles
C10 V8 + V13 RLS is enabled and anonymous callers cannot read protected records
Each has an expected failure assertion. For example, a spoofed cross-tenant insertion should
fail:
select throws_ok(
$$ insert into app.student_records (id, tenant_id, owner_id, display_name)
values (
'66666666-6666-6666-6666-666666666666',
'tenant-t2-id',
'student-a-id',
'spoofed T2 row'
) $$,
'new row violates row-level security policy for table "student_records"',
'student A cannot insert a record into T2'
);
A blocked update commonly produces zero affected rows rather than an exception:
select results_eq(
$$ with x as (
update app.student_records
set display_name = 'blocked-T2-write'
where id = 'record-owned-by-T2'
returning id
)
select count(*) from x $$,
$ values (0::bigint) $,
'student A cannot update T2 record'
);

supabase/tests.
The generated workflow has four jobs:
1. pgtap-rls — starts an isolated local stack and runs the RLS suite.
2. application-security — runs type checking, Jest/Vitest, SAST, and dependency auditing.
3. secrets-and-workflow — scans Git history and rejects mutable GitHub Action tags.
4. merge-security-gate — succeeds only when all prior security jobs succeed.

The generated test file uses jose and asserts:

Core verification code:
const { payload } = await jwtVerify(token, testKey, {
algorithms: ["HS256"],
issuer,
audience,
currentDate: now,
maxTokenAge: "60m",
clockTolerance: 0,
});
if (!payload.sub) throw new Error("missing subject");
if (payload.role !== "authenticated") {
throw new Error("invalid role");
}
The test key is deliberately ephemeral and only for local unit tests. Replace the production
implementation with your trusted issuer/JWKS or Supabase verification configuration—never
embed a production signing secret in frontend, test code, or GitHub Actions. JWT verification
should validate the signature and claims such as issuer, audience, subject, and expiration.
