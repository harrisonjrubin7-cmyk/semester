The matrix intentionally starts each control as NOT_VERIFIED; actual evidence and test
execution must change that status.
AC-03 demonstrates that a synthetic user in tenant T1 cannot access a record in tenant T2. It
needs three proof points:
1. Fixture sanity: confirm both T1 and T2 records exist outside RLS before testing.
2. Positive control: prove the T1 user can access a permitted T1 record.
3. Negative control: prove the same T1 user receives zero rows and causes zero mutation on
the protected T2 record.
The generated SQL template follows this pattern:

-- Fixture setup only: privileged local test role.

$ select 1 from app.student_records where id = 'record-t1' $,
'T1 student can read authorized T1 fixture'
);
-- Negative: Student A cannot see the T2 fixture.
select is_empty(
$ select 1 from app.student_records where id = 'record-t2' $,
'T1 student cannot read T2 record'
);
-- Negative: attempted update causes zero affected rows.
select results_eq(
$$ with attempted as (
update app.student_records
set display_name = 'blocked-test-write'
where id = 'record-t2'
returning id
)
select count(*) from attempted $$,
$ values (0::bigint) $,
'T1 student cannot update T2 record'
);
rollback;
An RLS-filtered SELECT or UPDATE may return zero rows instead of raising an exception. That is
why the test asserts result emptiness and affected-row count rather than expecting every denial
to throw. For rejected inserts, use throws_ok; pgTAP/Supabase guidance notes that blocked
inserts commonly raise an RLS-policy error, while blocked updates may simply affect no
records.

A logged-in student can replace recordId with another userʼs UUID. UUIDs make discovery
harder, but they do not prevent IDOR if an identifier is leaked, shared, obtained from an export,
or exposed by another endpoint. OWASP recommends per-object, server-side authorization
checks for every access attempt.
1. Derive the authenticated user from a validated server session or JWT.
2. Resolve active tenant membership and capabilities from trusted records.
3. Enforce resource authorization at the database layer with RLS.
4. Use a caller-scoped Supabase client for ordinary user requests so RLS is evaluated.
5. Do not use a service-role client for normal student access. If a privileged backend worker is
necessary, independently validate user, tenant, capability, and resource before the bypass-
capable query.
6. Repeat authorization enforcement for files, RPCs, exports, realtime, caches, search indexes,
views, and background jobs.
7. Add AC-03 pgTAP coverage plus direct API integration tests.
A policy concept should combine verified tenant membership and per-record authority:
-- Illustrative only: adapt to confirmed Semester tables and helpers.
create policy "verified tenant member reads own record"
on app.student_records
for select to authenticated
using (
owner_id = auth.uid()
and exists (
select 1
from app.tenant_memberships m
where m.tenant_id = student_records.tenant_id
and m.user_id = auth.uid()
and m.status = 'active'
and app.has_capability(
auth.uid(),
student_records.tenant_id,
'student_records.read'
)
)
);
Staff access should use a separately scoped and tested rule; do not accidentally turn a staff
permission into a broad cross-institution read policy. Also review SECURITY DEFINER functions,
execution grants, function owners, and search_path independently: a correct table policy can
still be bypassed by a poorly designed privileged function.

.github/PULL_REQUEST_TEMPLATE.md
GitHub automatically shows a pull-request template when it is stored in .github, the repository
root, or docs; multiple templates can live in .github/PULL_REQUEST_TEMPLATE/ and be selected
with a query parameter.
The template requires authors to declare:
Whether authorization, RLS, APIs, roles, data flows, uploads, exports, secrets, integrations,
CI/CD, or AI authority changed.
The affected assets, data classes, tenants, and rollback plan.
Results for type checks, unit tests, secret scanning, SAST, dependency review, and database
tests.
Direct API/RPC, positive authorization, cross-user, and cross-tenant testing.
Review of RLS, grants, protected columns, WITH CHECK, direct function execution, SECURITY
DEFINER, storage, exports, realtime, and background jobs.
Relevant ASVS 5.0 requirement IDs, control IDs, evidence links, exceptions, and expiry
dates.
A PR template prompts the right disclosures but does not enforce them. Pair it with required
branch protection checks for the security workflow, database policy test job, code review, and
protected production deployment approval.
