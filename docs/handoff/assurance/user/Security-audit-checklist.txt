The runbook covers these ten student-app risks:
1. SQL injection through filters, search, imports, or raw query building.
2. Stored, reflected, and DOM-based XSS in profiles, messages, rich text, and admin views.
3. RLS bypass / BOLA, where one student or institution accesses anotherʼs data.
4. Broken role escalation through client-controlled role, owner, grant, or approval fields.
5. JWT/session flaws involving expired, forged, revoked, or stolen sessions.
6. IDOR in files, exports, attachment paths, signed URLs, and derived views.
7. Unsafe file upload, including dangerous types, spoofed MIME types, and public-object
exposure.
8. CSRF and cross-origin state changes where cookie-based authentication is used.
9. SSRF through document import, link preview, URL fetches, or integration callbacks.
10. Secret leakage and insecure CI behavior, including privileged service keys exposed to
browsers or unsafe GitHub Actions workflows.
For every vulnerability, the document supplies an authorized validation approach, primary
remediation, and expected regression proof. Cross-tenant authorization matters most for
Semester because a student-data platform must prevent both cross-user and cross-institution
access through every path—not merely through the visible UI.

Mapping ASVS 5.0
The high-priority mapping order is:
1. V8 Authorization — RLS, role/capability checks, RPCs, storage, realtime, exports.
2. V6/V7/V9/V10 — authentication, session revocation, JWT handling, OAuth/OIDC if used.
3. V14 Data Protection — student data inventory, retention, exports, backups, and logging.
4. V4 API and Web Service — route inventory, schemas, authorization, webhooks, and limits.
5. V1/V2/V3 — encoding, validation/business rules, React/browser defenses.
6. V5 — private file storage and signed URL handling.
7. V13/V15/V16 — configuration, CI/CD, dependencies, defensive coding, logging/errors.
8. V11/V12 — cryptography, key lifecycle, TLS, and integration trust.
9. V17 — mark Not Applicable only aer confirming WebRTC is absent.
ASVS 5.0 separates authorization into V8, API security into V4, data protection into V14, and
logging/error handling into V16. It also adds separate areas for self-contained tokens,
OAuth/OIDC, and WebRTC.

It uses the ordinary pull_request trigger, read-only GITHUB_TOKEN access, and avoids
deployment or service-role secrets. It explicitly avoids pull_request_target because GitHub
warns that checking out or executing untrusted pull-request code under that privileged trigger
can compromise the repository and its secrets.

AC-03 proves that a T1 user cannot access T2 data. It must be tested with distinct synthetic
users and institutions, then repeated across direct API access, RPC functions, database policy
enforcement, exports, file storage, derived/cached data, and realtime subscriptions.
The key setup is to use an application-facing database role and a simulated authenticated JWT
context, not a database owner or service-role connection. Supabaseʼs testing guidance
specifically calls for setting the local role and JWT claims when diagnosing RLS behavior.
Example diagnostic template:
begin;
set local role authenticated;
set local "request.jwt.claims" =
'{"sub":"student-a-id","role":"authenticated"}';
-- Student A from tenant T1 tries to read a T2 record.
-- Expected: zero rows, with no sensitive data in error output.
select id, tenant_id, owner_id
from app.student_records
where id = 'record-owned-by-student-c-in-tenant-t2';
-- Expected: zero rows updated.
update app.student_records
set display_name = 'should-not-write'
where id = 'record-owned-by-student-c-in-tenant-t2';
rollback;
A zero-row result may be the correct RLS denial behavior. First prove the T2 fixture exists using
an authorized T2 test account, and prove the T1 account can read its own authorized record;
otherwise, an empty result might indicate bad fixtures or a globally broken policy rather than
correct tenant isolation. The detailed generated walkthrough includes safe savepoint handling
for expected rejected inserts, required evidence fields, side-effect checks, and remediation
steps when a path fails.
