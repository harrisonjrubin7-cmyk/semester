Key assertion pattern:
set local role authenticated;
select set_config(
'request.jwt.claims',
'{"sub":"student-a-id","role":"authenticated"}',
true
);
select is_empty(
$$ select 1
from app.student_records
where id = 'record-owned-by-t2' $$,
'student A cannot read T2 record'
);
select results_eq(
$$ with attempted as (
update app.student_records
set display_name = 'blocked-cross-tenant-write'
where id = 'record-owned-by-t2'
returning id
)
select count(*) from attempted $$,
$ values (0::bigint) $,
'student A cannot update T2 record'
);
The positive T1 assertion is essential. Without it, a “deny” test can falsely pass because fixtures
are missing or the policy denies every user. Supabase supports pgTAP database testing and
documents role/JWT-context testing for RLS behavior.
Before running, replace the placeholder schema/table names, UUIDs, and fixture-procedure
comments with the confirmed Semester schema. The file must run with authenticated for
enforcement assertions—never postgres or service_role.

Example:

algorithms: ["HS256"],

JWT validation should explicitly constrain accepted algorithms, issuer, audience, expiration,
signature key, and application-specific claims. The jose verifier supports accepted algorithms
plus issuer, audience, current date, and maximum-token-age checks.
Replace the test-only HS256 secret with your real production verification mechanism—typically
a verified JWKS/public key or trusted Supabase auth configuration. Do not reuse the test secret
or add production tokens to source code.

The runbook maps these risks to automated controls:
1. SQL injection → Jest validation tests and SAST.
2. XSS → React rendering tests and SAST.
3. RLS bypass / IDOR → pgTAP AC-03 plus direct API tests.
4. Role escalation → pgTAP protected-field/grant tests.
5. Token or session flaws → JWT Jest tests plus revocation tests.
6. File/export IDOR → API and storage policy tests.
7. Unsafe uploads → upload validation and storage policy tests.
8. CSRF/CORS failures → browser/API state-change tests.
9. SSRF → URL allowlist and redirect validation tests.
10. Secret/CI supply-chain risk → Gitleaks, dependency audit, and immutable action pinning.
Branch protection must independently mark appsec-unit, secrets, rls-policy, and at least one
code review as required. A workflow file reports failures, but branch protection is what
prevents those failures from being merged.
