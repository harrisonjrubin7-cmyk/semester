## D-1356 · The three registration actions the access saga names now have policy rules; the role and scope vocabulary is proposed, not confirmed

**Decided 6 Oct 2026**, on the owner's instruction to continue with C-5 and C-1. Context and backlog are in [`docs/master/SEMESTER_NATIVE_PDF_DELTA.md`](../master/SEMESTER_NATIVE_PDF_DELTA.md); the first half is [D-1338](D-1338.md).

- **What was decided.** `registration.readiness.view`, `registration.override.request` and `registration.override.approve` each have a rule in `packages/institution/src/policy.ts`, a refusing test in `policy.test.ts`, and an audit event type in `events.ts`. Before this, `decide` denied all three (ADR 0007), so the saga's request schema could never get an `allow`.
- **Step-up stays an obligation.** `decide` still returns allow-with-obligations or deny. `sagaOutcomeOf` reads a `require_fresh_mfa` obligation as the saga's `require_step_up`. `require_approval` is not produced: approval is its own action with its own rule. Every refusal runs before the MFA obligation is added, so a request that would be refused is never asked to step up.
- **Approval is bound.** An approval must name the request digest and the record version it reviewed, and both must still match; the approver cannot be the student; the request must be pending review.
- **Proposed, not confirmed.** Roles `academic_advisor` (scope `advisee`, scope id the student) and `registrar` (scope `tenant`), and the field lists per relationship (an advisor sees blockers but not the detail of a hold). Nothing in the repository settles these; the owner confirms or changes them.
- **Readiness data is not a precondition.** A reader whose readiness data is missing is still authorized; "unknown" is the evaluator's finding, not a policy refusal.
- **Held by.** Ten deliberate removals of a guard each turned a test red; the unmutated control stays green.
- **Not done.** The pilot's outcome states and ten-step order against the registration engine's check order (N-3), and any caller.
- **C-1: the component registry is files, not tables.** `docs/control-plane/components/<componentId>.component.json`, checked by `registry-files.test.ts`: valid shape, filename equals componentId, `implementation.repositoryRef` is a path that exists in this repository, and `checkRegistry` finds no missing provider, double provider or double authoritative writer. Files are reviewed like code and reverse with a revert; tables would need an applied migration and have no reader yet. The directory is empty, so nothing is registered, and a definition can only be added for code that exists. When something outside the repository must read the registry at runtime, load these files into tables, not the other way round.
- **C-6 is not in this change.** A Postgres store for the saga is a migration, and a merged migration reaches the connected project; it waits on the owner's choice between applied migrations and another route.
