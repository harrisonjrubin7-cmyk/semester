## D-1661 · A student's document is kept on the server as a workspace object whose versions never change, and a share names either the live object or one exact version

**Decided 2026-10-20**, by the assistant building the foundation for "work in a private Semester document, have a submission capture an exact version, then choose what to publish". The founder can overrule any of it. Nothing here is applied to a hosted database. Merging to main applies migrations to the canonical project, so this waits on the owner.

**1. New tables, not an extension of an existing one.** Main has nothing that keeps a document on the server with versions:

- `notes` (`20260901000700_records.sql`) is one jsonb row per note, written over in place by sync.
- `productivity_workspace` is a single blob per account, replaced whole under a sequence number. It holds tasks and plans.
- The editor's documents (`lib/document.ts`), their 20-deep history (`lib/docversions.ts`, IndexedDB) and unsent drafts (`lib/draft.ts`, localStorage, never synced) all live on the device.
- `packages/institution/src/assignment-submission.ts` models a private draft and a submission in memory, with no Postgres adapter.

Extending `notes` or the blob would mean either rewriting rows that must never change or bolting versions onto a sync format. So `20261022120000_workspace_objects.sql` adds `workspaces`, `workspace_objects`, `workspace_object_versions`, `workspace_object_grants` and `workspace_object_operations`, and leaves all of the above exactly as it was. The target architecture (`docs/target-architecture/04-DOMAIN-BOUNDARIES-AND-OWNERSHIP.md` §2) already puts "note, document, sheet, deck, file" in the productivity module under student authority, private by default. That is where these tables belong. The blueprint called the tables `objects`, `object_versions` and `sharing_grants`. They are prefixed here because `public.objects` would read as Supabase's `storage.objects`, and the repository already has several unrelated share tables.

**2. Tenant safety is enforced by foreign keys.** Objects are `unique (workspace_id, id)`. Versions reference that pair and are `unique (workspace_id, object_id, id)`. `workspace_objects.current_version_id` references `(workspace_id, id, current_version_id)`, so an object can only ever name one of its own versions. A grant's pinned version references the same triple. Every child also references `workspaces` directly with `on delete cascade`, so account deletion reaches each table in one step.

**3. A version never changes.** A trigger refuses any UPDATE, except clearing `created_by` when that account is deleted. It refuses DELETE while the version's object and workspace both exist, so only the owner's account deletion can remove one. No API role may write any of these tables directly. Every write goes through six `security definer` functions: `workspace_object_create`, `workspace_object_save`, `workspace_object_grant`, `workspace_object_revoke`, `workspace_objects_mine` and `workspace_object_read`.

**4. Saves are optimistic and idempotent.**
- `revision` goes up by one per saved version, and a save names the revision it read. Any other revision is SQLSTATE 40001, and nothing is written.
- Keys go on a ledger of their own (`workspace_object_operations`), because the gradebook's ledger is keyed by school and a personal workspace has none.
- The ledger records ids and SHA-256s of the title and body, never the text.
- The same key with the same request replays the first receipt, even after the revision has moved. The same key with a different request is 23505.

**5. Sharing.**
- A grant names one account and one target: the live object, or one version.
- A pinned grant reads that version and nothing else. That excludes the object row, its current title and revision, and any later version.
- A grant's target, grantee, permission and expiry can never change after it is made. Only revocation changes a grant, and revocation cannot be undone. So a pinned grant cannot become live access.
- A live grant reads the object and its current version, and follows the object to each new version.
- `edit` exists only on live grants and lets the grantee save a new version. `comment` reads, because there is no comment store yet.
- Only the owner grants or revokes. Expired and revoked grants give nothing.
- No access comes from a school, an email domain or a link: the check suite's stranger shares both with the owner and is refused everywhere.

**6. Audit, not events.** Every create, save, grant and revoke, and every read by someone other than the owner, calls `private.record_audit`. The object id is hashed, there is no title or content, and the tenant is null, so only the service role can read these rows. No domain event is emitted, for two reasons. `private.emit_domain_event` needs an existing tenant on every row. And `packages/institution/src/events.ts` has no type for a personal document (`submission.draft_saved` is the LMS's). Adding both is a decision for when something consumes the events.

**7. No capability.** Ownership is `auth.uid()` against `workspaces.owner_id`. There is nothing for a role to hold, so `app_capabilities` and `capabilities.check.sql` are untouched.

**8. The client, without a screen.** `app/src/lib/workspace/objects.ts` maps errors as follows:

- 40001 → "This changed since you opened it. Reload…" (`stale`)
- 23505 → `conflict`
- an undefined function or table → "not set up at your school yet. Your work is still on this device." (`not-set-up`)
- anything else → the server's own sentence (`refused`) or `unknown`

It is not wired into `screens/Write.tsx`. An opt-in "Save a version to Semester" action needs these: a mapping from a device document to an object id and revision, a stale-reload flow, the full set of states, and screenshots. That is a separate piece of work.

**9. Measured.**
- `supabase/workspace-objects.check.sql`: 105 checks. The full `check.sh` run (PostgreSQL 16) passes 158 suites and 6,066 checks.
- Nine guards were each shown red against a revert, then restored: the version trigger, pinned-to-live, owner-only grant, the current-version foreign key, the stale check, replay request comparison, the grant trigger, expiry and revocation.
- One limitation of the suite: a single-transaction suite cannot run `delete from auth.users` over rows it inserted in that same transaction. Postgres rechecks the foreign key of a row this transaction inserted when `created_by` is set null. So the suite proves the workspace cascade and the `created_by` clear separately. The auth delete itself was run across two transactions by hand and removed every row.

**Owner decisions defaulted here**, any of which can be changed before this is applied:

1. **Content is inline text**: `text/plain`, `text/markdown` or `application/json` with a `content_schema` such as `semester.document/1`. Private storage keys for binary files and uploads are not supported. A `file` object today holds text.
2. **At most 1 MiB per version**, measured in UTF-8 bytes. There is no cap on the number of versions or objects, and no quota.
3. **Personal workspaces only.** `workspaces.kind` admits `personal`. Institution or course workspaces, and members other than the owner, are later.
4. **Retention**: kept until the owner deletes their account. There is no clock, no retention sweep and no legal-hold path. All three would need a deliberate exception in the version trigger.
5. **`edit` grants can save versions**, and the version records the editor as `created_by`. They cannot share onward.
6. **A live grant reads only the current version**, not the history.
7. **Grantee reads are audited and owner reads are not.** Refused reads are not audited, because the refusal's transaction rolls back.
