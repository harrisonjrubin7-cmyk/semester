## D-1251 · Client roles lose the table privileges row-level security does not govern, and the shared key stops serving school accounts

**Decided 2026-10-05**, on the owner's instruction to apply the grants migration to production and to treat a school's students as the school's to govern.

**Grants.** `supabase/migrations/20261005000000_client_roles_lose_table_ddl_privileges.sql` revokes `TRUNCATE`, `TRIGGER`, `REFERENCES` and (Postgres 17) `MAINTAIN` from `anon` and `authenticated` on every `public` table and in the default privileges for new ones. No row privilege changes. `supabase/client-privileges.check.sql` holds it, with a planted-grant control; it was seen red on the unmigrated schema. It was **applied to production on 2026-10-05** by running the statements and writing the ledger row by hand (nothing pending sat below it). Catalog read before and after: holders of the three privileges 150 to 0, `MAINTAIN` 50 to 0, SELECT/INSERT/UPDATE/DELETE counts unchanged (306/133/105/113). Not covered: tables created by `supabase_admin` in `public` still default-grant all eight privileges, and the `anon` DML reduction and the `authenticated` allowlist still need decisions (`database/GRANT_ALLOWLIST.md`). Rollback is a forward migration granting the four back.

**Shared key.** `supabase/functions/claude/index.ts` refuses an account whose `profiles.school_id` is set (403) and one whose school cannot be read (503), before the plan is read or anything is counted (`supabase/functions/_shared/tenantai.ts`, `app/src/lib/tenantai.test.ts`). It is behind the provider-activation gate (`D-1031`), so it changes no one's service today; it is not deployed and not run on a Deno runtime. Serving a school's students through the shared key when the school has turned AI on needs a tenant policy check on the edge and is **not done**.

**Pages.** `app/src/lib/pagesdeploy.test.ts` holds that `pages.yml` is the only workflow that deploys to GitHub Pages, after two starter workflows raced it on 2026-10-04.
