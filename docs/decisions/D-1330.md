## D-1330 · Onboarding progress is written only by functions that check the caller; a hand-off is a routing request, not authority; the event contract exists and collects nothing

**Decided 2026-10-06**, in this pull request, on the founder's instruction to carry out four open items from the web-first journey reconciliation (D-1315's follow-ups). The founder, or the privacy owner, can overrule it. It is **not** the owner decision D-4 in `docs/marketing/MARKETING_SITE_BACKLOG.md`: nothing here turns collection on.

**Context.** `public.onboarding_progress` lets a client write its own completion and has no version, so changing the tour cannot be told from a student skipping it. The journey PDFs ask for the server to hold the durable truth. They also ask for a hand-off from a public link into the app that carries no token and grants nothing, and for a funnel event taxonomy. `MARKETING_ANALYTICS_EVENT_TAXONOMY.md` §2 lists six preconditions for collecting anything, none of which is met.

**Decisions.**
1. Four new tables (`onboarding_journeys`, `onboarding_assignments`, `onboarding_step_progress`, `onboarding_events`) are readable by their owner and writable by no client. Every change is `start_onboarding`, `complete_onboarding_step` or `skip_onboarding_step`, each reading the caller from `auth.uid()`. A step is checked against the journey version the assignment was made under; a required step cannot be skipped; a retry writes nothing twice. `onboarding_progress` is left as it is.
2. A link's facts are kept as a short allowlist (a fixed source list, three id fields of `[A-Za-z0-9_-]{1,64}`, a role hint, one of ten screens), applied in the database (`private.entry_context`) as well as in the browser. A role hint is never an authority, and `tenant_id` on an assignment is set only by the service role after it has checked a membership. `entrycontextparity.test.ts` fails if the two allowlists drift.
3. A hand-off (`handoff_transactions`) is created only by the service role, stores a hash of its nonce, lives at most fifteen minutes (a table check, not only the function), is used once, and answers null for every way of failing, without using up the nonce on a wrong guess. It names a screen from the same ten and the app still decides what the account may open.
4. Every new function revokes `EXECUTE` from `public` **and** from `anon` by name. Supabase's default privileges grant it to `anon` directly, so revoking from `public` alone left a signed-out visitor able to reach `consume_handoff`; the suite caught it on its first run.
5. The marketing event taxonomy exists as a typed contract with an allowlist and a no-op sink (`lib/marketingevents.ts`), which is what taxonomy §2 says to build until its preconditions pass. Unknown fields are refused, five server-observed events cannot be built in the browser, consent is fail-closed, and a test fails if any other file builds a tracker, so turning collection on is a deliberate edit.
6. The company site's links into the app carry `src`, `cid`, `content` and `role=student`. `role` is sent only as `student` because every app link there is for an individual; institutional paths do not link into the app.

**Not done.** The migration is not applied to any live project. No journey is published and the app does not call the functions yet. No Edge Function creates hand-offs and no native client consumes them. Collection is off. An institution-facing adoption read needs a cohort floor and a consent decision first.

**Consequences.** Nothing a student sees changes. Applying the migration adds five tables and six functions, one scheduled job (`handoffs`, daily), and nothing that existing rows depend on.
