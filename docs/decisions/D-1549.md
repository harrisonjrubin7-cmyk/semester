## D-1549 · A registration swap lands in a seat, or nothing changes

**Decided 2026-10-18.** A swap — giving up one section and taking a seat in another section of the same term — is one transaction, `registration_swap`, and it either completes or leaves the student's enrollment as it was.

- **The drop is written first.** The add is then judged on the schedule the drop leaves, so a clash or a credit ceiling caused by the section being given up does not refuse the swap. A plain enroll into the same section is still refused for that clash.
- **A refused add rolls the drop back.** The drop and the add run in a nested block. Any refusal from the add raises inside that block, so the drop is undone with it and the function returns the refusal. The student keeps the enrollment they had.
- **Seat only.** A swap into a full section refuses with `full`, or `stale_seat_count` when the student confirmed a seat that is gone. It never puts the student on a waitlist, because that would cost them the section they hold. An approval-required section refuses with `approval_required` instead of creating a pending request, because the drop would already have been written.
- **A hold stops the swap before anything moves,** since the add is blocked. The student can still drop on their own.
- **The idempotency record takes a `swap` action.** Its check constraint is widened to allow it.

**Not done:** no HTTP route (REG-5.11 stays partial); no run against PostgreSQL 17 or the remote project, which needs approval; no interface for it.
