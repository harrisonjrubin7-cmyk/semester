## D-1500 · The scheduled tick ships with no participants, and says so in its answer

**Decided 12 Oct 2026.** The access saga tick (D-1492) ran only in tests. The shape for running it in production already existed: an Edge Function with a bearer token the database checks against Vault and a `pg_cron` job that posts to it (`integration-tick`, D-856's arrangement). The question was whether to schedule a worker that has nothing real to run yet, and what it should do when called.

- **What was decided.** `access-saga-tick` is deployed in the integration tick's shape: a generated copy of the tick, the store and the runner under `_shared/access-saga/`, held to its source by a test; `serveTick` shared unchanged; a token check of its own, `access_saga_tick_authorized`, over a Vault secret of its own. The participants live in `access-saga-registry.ts` and it holds `null`. With `null` the scheduled entry asks the database what is due, claims nothing, and answers `outcome: unregistered` with the count. The `access-saga-worker` job is in `scheduler.sql`, parked.
- **Why schedule it before there is anything to run.** Every piece on the way from the clock to the runner is now exercised in the shape it will have: the job's cadence, the Vault secret, the token check, the service-role client, the copy, the due list. Registering participants later changes one file and nothing around it. The alternative, writing all of this with the first real participant, puts the plumbing and the participant in one change and one review.
- **Why the unregistered tick counts rather than returning nothing.** A count of due sagas on every tick is the signal that something is waiting for a participant; a bare 200 would hide it. Counting is a read of a list the function already exists for; claiming would take leases for nothing, as D-1492 ruled out.
- **Why a secret of its own and not the integration one.** One Vault row per scheduler means rotating one token touches one job. A shared row would couple two schedulers' rotation for the sake of one fewer `do $$` block.
- **Why parked.** The function has no reading yet (`functions.snapshot` carries its pending row), and a job that posts to a function nobody has read is a job whose first failures nobody is looking at. `integration-sync` was parked until its test request answered 200; this follows it, with the request and the unpark statement in `DEPLOY.md`.
- **Why the runner's `call` became `participant`.** The EDGE-FUNCTIONS register reads `call('name'` in a function's closure as a database call, and `evaluate` has no migration. Renaming one local helper is cheaper than teaching the register that this one `call` is different, and the register's rule is worth keeping blunt.
- **Held by.** `access-saga-tick-auth.check.sql` at 9 checks (pointed at the wrong Vault row: "the stored secret is accepted — expected t, got f"); `edge-access-saga.test.ts`; 5 unit tests of the scheduled entry including one that fails the day participants are registered; one adapter rehearsal that shows the unregistered tick counting one due saga and leaving it untouched, and the same call moving it once participants are handed in; the scheduler, deploy, function-config, snapshot, edge-guard and register tests that hold the job and function to every file that names them.
- **Not done.** The job is parked until the function's first deployment answers the test request. No real `Services`: the registry is null and the delta document's C-6 row says so. The revocation barrier at a real enforcement point stays open.
