## D-1483 · The shared key has a daily token quota per account, and it ships with no quota

**Decided 2026-10-11**, on the owner's instruction: add a daily token quota per account and set it to no limit. The instruction is the decision; the setting exists so that an operator can turn a ceiling on without a deploy.

**What.** `TOKEN_QUOTA_DAILY` on the `claude` Edge Function is tokens per account per UTC day, counting every token Anthropic reports (input, output, cache read, cache write). **Unset is no quota**, and so is the empty string a deploy writes, `0`, `unlimited`, `none`, `off`, `max`, or anything that is not a positive whole number (`supabase/functions/_shared/tokenquota.ts`, `dailyTokenQuota`). While there is no quota the function never calls the meter and writes nothing. When a number is set, the worst case — counted input plus the whole `max_tokens` — is reserved by `public.add_tokens` against `public.usage_daily` right after the dollar reservation (D-1231) and before the school's budget, settled to actual use where the dollars are settled, released wherever they are released, and left standing when the fetch throws or the stream ends unread. A spent quota is 429 with `error.code = 'token_quota_exhausted'` and a sentence carrying `today's shared AI token quota`, which `app/src/lib/claude.ts` passes through instead of "wait a moment"; every forwarded answer then carries `X-Tokens-Remaining`, the quota less the meter's latest answer: settled use for a plain answer, the released day for a refused upstream, and the reservation for a stream, whose headers leave before its usage block (it errs low). The sixty-call count and the dollar allowance are unchanged and still apply.

**Why.** The two existing meters are monthly. A burst inside one day — a script, a stuck client — reaches the monthly caps only after the money is spent. A per-day ceiling is the tool for that, and the owner's call is that it starts off: the public offer and `lib/allowance.ts` still say "sixty a month", and nothing new is said to a student until somebody chooses a number.

**The edges.** *A separate table* (`usage_daily`, keyed by account and `YYYY-MM-DD`), because `usage.month` is documented as `YYYY-MM` and a day row in it would be a second meaning for the same column. *Invalid is unlimited, not a guess*: the default is already unlimited, so an unreadable value falls back to the default like every other optional setting here. *A meter that cannot answer refuses*, as the other two do. *An uncapped charge is recorded* even when it passes the reservation, so a day that cost more than it should is visible rather than hidden.

**Not done.** No client copy of the quota is shown anywhere (nothing to show while it is unlimited; a chosen number would want the same `allowance.test.ts` treatment the monthly figure has). `supabase/health.sql` block 1 does not yet read `usage_daily`. The migration version moved to `20261011210000` because #1479 landed `20261011200000` first.
