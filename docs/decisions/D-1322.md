## D-1322 · The billing webhook reads Stripe events through the payment-rail adapter, held to a recording of what it did before, with nothing else changed

**Decided 6 Oct 2026**, as the next step of D-1319 (action 8 of `docs/finance/NATIVE_FINANCIAL_PLATFORM.md` §14), taken on the owner's instruction to merge #1319 and continue.

- **What was decided.** `supabase/functions/_shared/billingwebhook.ts` no longer verifies a signature or reads a Stripe event shape itself. It asks `createStripeAdapter` to verify and normalize, then maps each normalized event to the same four service-only SQL functions it always called. Its HTTP answers, its `WebhookDeps` and the order of its checks are unchanged. A request the adapter cannot turn into an event is refused (400) rather than reported as recorded; that state is unreachable today.
- **Why a recording and not a comparison.** Once the handler and the normalizer share code, comparing them proves nothing. The 25 fixture events were run through the handler **before** the move and its 31 database calls kept as `app/src/lib/payments/stripe.golden.json`; the handler as it now is and the normalizer are both held to that file.
- **Held by.** `normalize.test.ts` (84 payments tests with the golden record), the existing `webhook.test.ts` and activation tests passing unchanged, five planted bugs in the new apply step each shown red, and `webhookseam.test.ts`, which fails if the handler names a Stripe event field or signature routine again.
- **Stays as it is.** No event is newly acted on: refund and dispute events still change nothing beyond what the handler already recorded (their effects are actions 16 and 17). `billing-checkout`, `billing-cancel` and `billing-portal` are untouched, no SQL or migration changed, and both checkout-hold constants stay false. D-146, D-1236 and D-1319 stand.

**Not decided here and not done.** Deploying the function is the owner's, through the existing functions workflow; the move was proved against the handler's tests, not against a live Stripe event. Parking an invoice event that arrives before its subscription instead of answering 500 (action 8's second half in the plan, with the event inbox and dead-letter) is a separate change and needs the inbox migration. No price, threshold, counsel decision or PCI determination.
