## D-1063 · A school says per Core module and data class whether AI may be used (default no), five classes are never permitted, and every answer is logged; nothing calls it yet

**Decided 1 October 2026.**

Core prompt 13 is titled "AI across the operating system". It is not read as a
mandate to add AI to modules. DO-NOT-BUILD rule 3 (nothing ranked or suggested
that nobody can explain) and the repository's position (Semester is a
calculator over facts a school supplies; AI never decides) bind it. So the
question asked first was what AI governance already exists, and what is missing
across the Core modules.

### What already existed on `origin/main` (not rebuilt)

- **`ai_policy`** (`20260923210000_intelligence_policy.sql`): per school, the
  allowed modes (`explain`, `hint`, `practice`, `review`, `draft`), providers,
  web-source and course-source-only switches, a monthly budget and a retention
  setting; writes need `ai:configure`. Audited by `tenant_policy_audit_event`.
- **`tenant_feature_policy`**: a per-school, per-capability release state
  (`off` to `production`); it answers "is this capability on", not "may AI touch
  this module's data".
- **`data_classification_rules`** (`20260927170000_integration_control_plane.sql`):
  T0 to T6 ceilings, tenant rules only stricter than the platform's, T4 and above
  never in approved AI. Per classification, not per module; T3 education records
  are allowed in approved AI at the platform floor.
- **The institution gateway** (`app/server/institution/intelligence*.ts`,
  `packages/institution/src/intelligence.ts`): role, mode, approved sources only,
  model route under a cost ceiling, budget reservation, a journal
  (`gateway_intelligence_audit`) with category, provider, model, tokens and cost.
  Its input is `approved_source`, course sources a school approved.
- **`kill.ai_generation`**, `lib/toolkit/classification.ts` `gate()` and
  `policy.ts` (client side: T3 and above never leave the device to an AI path;
  an unrecorded course policy reads as no), the provider activation record
  (D-1031), provider terms (D-147, `docs/trust/PROVIDER-TERMS.md`), the
  evaluation harness docs, and the Socratic tutor's hint ladder.

### What was missing, verified by grep

1. Nothing says, **per school and per Core module**, whether AI may be used at
   all. The Core modules (D-151, `core_modules()`) each have a Connect/Core
   switch and nothing about AI.
2. Nothing keeps the five kinds of data a model must never be asked about as a
   closed list that **a policy row cannot override**. `data_classification_rules`
   refuses looser-than-platform rows, but T3 (grades, rosters, advising notes)
   is allowed in approved AI at the floor, and no rule names admissions
   decisions or aid amounts.
3. Nothing is a **log of each AI use decision** that touched a module: the
   gateway journal records calls made, not questions asked and refused, and it
   names no module or data class.

### What was decided

- **A policy per school, module and data class.** `ai_use_proposal` and
  `ai_use_approval`, append-only (revoked privileges, definer RPCs, immutability
  triggers). The default for every module is **no**. Turning AI on needs a
  second person with `ai_use:approve`, never the proposer, within seven days
  (the Workflow Builder's two-person publication, D-1018, and the module-mode
  approvals, D-151). Turning it off applies at once: reducing what AI may do
  waits for nobody. New capabilities `ai_use:propose`, `ai_use:approve` and
  `ai_use:read` for `university_admin`, and `ai_use:read` for `registrar`.
- **Five never classes** in `private.ai_use_never_classes()`:
  `grade_or_transcript`, `admissions_decision`, `aid_amount`, `disciplinary`,
  `health`. They cannot be the class of any policy row (a CHECK against the
  permittable list, so the table's owner cannot write one either), and the
  decision answers `never_class` first, before any module or policy is read, so a
  school cannot enable them and a yes on file for another class changes nothing.
  The five permittable classes are `catalog_public`, `schedule_structure`,
  `instructor_material`, `requesters_own_work` and `deidentified_aggregate`. The
  two lists are the author's reading, **not reviewed by counsel or any school**.
- **`public.ai_use_permitted(school, module, data_class, actor, provider_name,
  model_name)`**, service_role only, returns `(allowed, reason)` and writes the
  log row in the same call. Order: never class, unknown module, unknown class,
  `kill.ai_generation`, no policy, denied by the school, permitted by the school.
- **`ai_use_log`**, append-only: who, module, class, allowed or denied, one of
  seven reasons, the provider and model names as text the caller supplied, the
  time. No column can hold a prompt or a response; a check reads the column list.
- **A register of the routes to a model** (`ENTRY_POINTS` in
  `app/src/lib/aiuse/spec.ts`): the four files that reach a provider. A test
  fails when a new one appears, and fails when any AI path imports a Core
  module's code, so the first route that reads a module's data cannot arrive
  without somebody calling the gate and saying so.

### What is not done

- **Nothing calls `ai_use_permitted`.** No existing route handles Core module
  data (the gateway receives only approved course sources; the Ask routes send
  the student's own planner; the shared-key relay is not activated). Wiring one
  would be invented. The policy decides nothing today: a stated gap, not a
  feature.
- **No screen.** No school-admin surface exists on main for the sibling
  administrator features, so a page would have no honest home.
- **No AI feature, model call, prompt or response storage**, evaluation harness
  change, provider contract or term (counsel's and the owner's, D-147),
  fine-tuning, embeddings, AI grading, AI admissions or cross-module
  recommendations.
- **Retention is not decided** for the three tables. The account ids on them are
  plain uuids with no foreign key, so deleting an account does not clear them;
  that is deliberate and written in `RETENTION.md` and `KEPT_TABLES`.
- An unknown school id is denied but cannot be logged (the log's foreign key).
  The provider and model names are whatever the caller supplied. No idempotency
  key is used. The migration is applied to no database and was run only on
  Postgres 16 (the live project is 17).
