## D-1026 · The advisor's policy-less tables and definer functions are classified, not silenced; the four missing indexes and two missing keys are fixed

**Decided 30 Sep 2026.** Production's advisor was read, read-only, at 13:46 UTC:
49 tables with row-level security and no policy, 180 signed-in-callable
`security definer` functions, four foreign keys with no index, two tables with
no primary key. `supabase/advisor-probe.sql` mirrors the four lints in
`pg_catalog`; on production it returns 49 / 180 / 4 / 2, so it is the advisor's
count, not a guess at it.

- **The 49 are not exposure.** None grants `anon` or `authenticated` any table
  or column privilege. That is the shape of a table only a definer function or
  the service key reaches. No policy is added: it would be the one thing that
  made a table reachable. Four are new to the register (45 to 49).
- **The 180 are the register's 180.** None is executable by `anon` or PUBLIC,
  every `search_path` is pinned. No grant changes. `kill_switch_engaged` stays
  open (DR-01) because three invoker callers need it; anon table privileges on
  26 tables are recorded as DR-04, not revoked in a change with no reader.
- **Fixed:** an index on `tenant_id` for each of the four tables, and a
  surrogate `id` primary key for `site_lead_hits` and
  `console_audit_verification`, whose identity sequences are revoked from every
  client role. `indexes.check.sql` now covers `private` and requires a primary
  key on every table, the gap that let these through.
- **Not applied to production.** The migration is a draft on a draft PR. The
  after reading on production is not taken until it is applied, which needs
  separate authorization.
- **Left alone:** `multiple_permissive_policies`, `unused_index` (new tables),
  and `auth_db_connections_absolute` (a dashboard setting).
