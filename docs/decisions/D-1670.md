## D-1670 · An employer reads a student's portfolio evidence only through a grant the student made to them, scoped to named pinned versions, ending within 180 days, revocable at once, and never including grades

**Decided 2026-10-21**, by the assistant building backlog item B25 (journey steps 9–10) on top of #1661. The founder can overrule any of it. Nothing here is applied to a hosted database. Merging to main applies migrations to the canonical project, so this waits on the owner. It also waits on #1661, which it stacks on.

**1. The employer is the identity the schema already has.** That identity is an account holding a live `role_grants` row with `role = 'employer'`, `scope_kind = 'employer'` and a `scope_id` naming the employer (`20260921223000_role_grants.sql`, `20260926150000_expansion_roles_and_features.sql`). RLS on `talent_profiles` and `opportunities` already uses it. A grant names both the account and the `scope_id`.

The account is found by address only among people who hold that role now, as `share_with_support` finds staff (`20260928308000_support_shares.sql`). The role is checked again at every listing and every read. An employer whose role grant is revoked or expires loses the evidence without the student doing anything.

The gateway's sandbox (`app/server/institution/career.ts`) models an employer as a row with an `approved`, `pending` or `suspended` state. That row is an in-memory demonstration and has no Postgres table. No new identity model was invented here. In the database, suspending an employer means revoking its role grant.

**2. Evidence is a pinned version, reusing #1661.** `career_evidence` references `workspace_object_versions (workspace_id, object_id, id)`, the same triple a pinned workspace grant uses. Evidence can therefore only name the student's own version, and #1661's trigger stops that version from ever changing. Nothing can name the live object.

The employer's read returns the pinned version's text and label. It returns no object id, revision or current title. After the student saves again, the employer still reads the version that was chosen.

**3. Employer access is not a `workspace_object_grants` row.** That table was considered first and does not fit, for three reasons:

- It names an account, not an employer principal whose role must be checked again.
- A grantee there reads versions directly through RLS, and nothing audits that read. Every employer read must be audited.
- It targets one object or version, while a student shares a set and revokes the set together.

So `career_evidence_grants` plus `career_evidence_grant_items` hold the share. Employers have no RLS policy on any table here or in #1661, and `private.workspace_object_access` is unchanged. `workspace_object_read` and the workspace tables answer an employer exactly as they answer a stranger. An employer reads only through `career_evidence_shared_with_me` and `career_evidence_read`, and both write `private.record_audit`.

**4. What is reused rather than copied.**
- The idempotency ledger `workspace_object_operations`, via `private.workspace_replay` and `private.workspace_spend`. Only its `kind` check is widened.
- `private.age_cleared` (D-139): minors are kept out of employer visibility, both when granting and at every read.
- The trigger shape that lets a grant only be revoked.
- `private.record_audit`, with tenant null and no content, as in #1661.

**5. Stale and idempotent.** Every student write (add, withdraw, grant, revoke) names the portfolio `revision` it read (`career_portfolios`). If the revision has moved, the write gets 40001 and nothing is written. A key reused with the same request replays the first receipt. A key reused with a different request gets 23505. Revoking or withdrawing twice answers the first time and does not move the revision.

**6. One answer for "no".** The employer gets `42501 no such evidence here`, word for word the same as for an id that never existed, in every one of these cases:

- the grant is revoked or expired;
- the employer no longer holds the role;
- the student is not age-cleared;
- the item was withdrawn;
- the item belongs to another grant or another student;
- the employer is a colleague at the same company or works for a different company.

**7. Grades.** No career function reads a grade table, and no grant has a grade field. The check suite tests this in two ways:

- **Behaviourally:** an employer holding a live grant sees no `grade_entries` or `gradebook_items` row, and `gradebook_export` refuses them, while the student sees their released grade.
- **Structurally:** it fails if any `career*` function's source names a grade table, or if any grade-table policy mentions career evidence. As a control, `gradebook_export`'s own source is shown to name the grade table, so the source check is known to work.

**8. Measured.**
- `supabase/career-evidence.check.sql`: 117 checks. The full `check.sh` run (PostgreSQL 16) passes 159 suites and 6,183 checks.
- Seven guards were each shown red against a mutation of the migration, then restored:
  1. revocation ignored
  2. expiry ignored
  3. the role not checked again
  4. the read returning the live object
  5. someone other than the owner granting
  6. a grade leak through a policy backed by a definer function
  7. the stale check removed
- The first grade probe was a plain policy whose subquery ran under the employer's own RLS, so it leaked nothing. Only the structural check caught it. It was rewritten as a definer-backed leak, which the behavioural check catches.
- `definer-sweep.check.sql` caught `career_evidence_mine` answering a stranger. It now expects exactly the stranger's own empty portfolio.

**Owner decisions defaulted here**, any of which can be changed before this is applied:

1. **Every grant expires, at most 180 days out.** There is no open-ended grant. The client's checks enforce the same 180-day limit and do not choose a default. A screen would propose one; 30 days is the suggestion.
2. **No grade summary in a grant, ever.** There is no field for one. Adding one would need its own decision and its own consent wording.
3. **Employers are not notified on revoke, or on grant.** Access simply ends, and the employer's listing stops showing it.
4. **A grant is 1–20 items and cannot be widened.** To share more, the student makes a new grant.
5. **The student names themselves (`shared_as`, up to 80 characters).** Nothing is looked up from their profile or school.
6. **The employer is found by email address plus employer scope id.** There is no employer directory or search. The student is told only that nobody at that employer uses that address.
7. **Withdrawing evidence ends access to it in every grant**, without revoking those grants.
8. **Refused employer reads are not audited**, because the refusal's transaction rolls back. Successful reads, and each grant an employer is shown in a listing, are audited.
9. **Career-office vetting is the role grant.** A pending or suspended employer state, as the sandbox models it, would be a new table and a new decision.
