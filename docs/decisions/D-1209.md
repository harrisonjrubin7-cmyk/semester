## D-1209 · Hold the import boundaries that already exist with a test, read by a tokenizer, and ratchet the one that does not

**Decided 2026-10-04.** The boundaries between `packages/`, `app/src`, `app/server`, `app/api` and `supabase/functions/` are held by `app/src/lib/importboundaries.test.ts`, which reads the whole tree through `app/src/lib/importgraph.ts`. Seven rules, each measured on the real tree before it was written. All hold with no exception except one: the 15 imports by which `app/server/integration` uses `app/src/lib/integration` are recorded in `SERVER_USES_CLIENT_LIB`, which can shrink and cannot grow, and a pair that goes must be deleted from it.

Why a tokenizer: TypeScript 7 exposes only `version` from its JavaScript entry point, so there is no compiler API, and adding a parser is a dependency that `docs/SUPPLY-CHAIN.md` would have to price. The reader was compared once with a real parser (rolldown's, inside vite 8) on 2,879 files and 12,754 specifiers, with no disagreement. That check is not in the suite because the parser is not a dependency of this repository.

Why these rules: each is something that already failed or nearly did. `check:university` cannot compile a module that imports `supabase/functions/` (#803). A built-in imported into anything the browser loads breaks at run time without failing the build, and five audit modules in `app/src` do import `node:fs`, safe only because nothing reaches them. A package that imports the app is not a package.

What it found on its first day: `main` at `372f8e2` could not run `npm ci`, because a new `packages/platform` was added without a root lockfile entry, and 13 of its test files imported vitest through the `app/node_modules` path that [D-1193](D-1193.md) removed. That is fixed by #1200, and this decision does not duplicate it.

Not decided and not done: the per-module `index.ts` and module-DAG rules wait for modules to exist (wave C1 onward). A dynamic import whose path is built at run time is invisible to this checker and to any parser.
