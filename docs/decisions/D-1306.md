## D-1306 · A signed-out visitor holds a table privilege only on the public catalog, the open forms and the school list

**Decided 2026-10-05**, by the assistant under the executive authority the founder delegated in-session (D-1287). The founder, or the privacy owner, can overrule it.

**Context.** `database/GRANT_ALLOWLIST.md` measured `anon` holding full row privileges on 32 `public` tables and one view (Supabase's default). Row-level security governs them and every policy denies `anon`, so no row access existed; but the grant was the only thing left to fail if a policy were ever written wrongly. The previous migration removed TRUNCATE, TRIGGER, REFERENCES and MAINTAIN and recorded this as an open decision.

**Decisions.**
1. `anon` loses every privilege on every `public` table and view, and is granted back only: SELECT on the pricing catalog (`commercial_plans`, `commercial_prices`, `commercial_products`, `entitlement_definitions`, `plan_entitlements`), `form_publications`, `published_forms` and `schools`; INSERT on `form_responses`.
2. `schools` stays readable by `anon`. Whether the full school list, with every column, is meant to be public to the signed-out is a product and counsel question this does not answer.
3. Supabase's default privileges are left alone (the local harness must keep modelling them). `client-privileges.check.sql` is the forcing function instead: a table added by a later migration fails it until that migration revokes the default from `anon`.
4. Five suites that asserted "a signed-out visitor sees none" by counting rows now also accept a permission refusal. The assertion that `anon` receives no row is unchanged.
5. Applying it to production is the owner's step, after reading what `anon` holds there that the migration does not name.

**Consequences.** A signed-out request for one of the revoked tables now fails with a permission error instead of an empty list. Nothing in the app read them before sign-in to any effect, since the answer was always empty.
