## D-1478 · The inception specification is a registry layer with gates, not a second catalog

**Decided 11 October 2026.** The execution specification of 11 October ("come on
continue") lists 25 operating systems, 673 screens and 51 roles and asks for every
one to be live from inception, with "live" meaning the full chain — tenant,
workspace, capability, screen, command, event, record, policy, integration,
audit, owner, runbook, tests, evidence — resolves. The repository already holds
a different count (40 master-catalog domains, 589 catalogued screens, 69
database roles) and an implementation control plane that refuses claims
without evidence. This records how the two were reconciled.

- **The repository's catalog stays the authority; the specification is mapped
  onto it.** Each of the specification's operating systems (26 are listed; the
  text says 25) is a registry record under
  `packages/platform-control/registry/operating_systems/` carrying the pilot
  release scopes it is delivered through and the D01–D40 domains it covers.
  Where nothing maps — admissions has no domain, a developer has no database
  role, 42 of the 54 minimum events have no `EVENT_TYPES` entry — the record
  says so in `gaps`, and the validator refuses a record that falls outside the
  catalog without saying so.
- **Nothing in the layer may claim operation.** An operating system cannot be
  `implemented` or `verified`; an adapter cannot declare `healthy`, `stale` or
  `degraded`; a journey is `verified` only with a named end-to-end test; an
  event is `implemented` only when its catalog type exists, and the catalog is
  read from `packages/institution/src/events.ts` rather than copied. These are
  the same refusals the workspace registry makes for pilot scopes
  (`b7a251a1`), applied to the new groups.
- **The database projection enforces the chain rather than describing it.**
  `supabase/migrations/20261012110000_platform_registry.sql` keeps the four
  registry tables in `private`, service-role only, and its triggers refuse a
  capability that is `deployed` or `active` below its workspace or any
  dependency's required status, `tested` without test evidence, or `active`
  without verified unexpired evidence, and a workspace that falls to `draft`,
  `blocked` or `retired` under a live capability. The files remain the
  authority; `generated/registry-projection.sql` is rendered from them with
  status derived from capability maturity, and nothing applies it
  automatically. The specification's sketch used `public` and an `accounts`
  table; this repository's conventions are `private` and `auth.users`.
- **The access policy baseline is a tested contract, not a second
  evaluator.** `infra/policy/access.rego` states the eight conditions in the
  order `packages/platform/src/policy/engine.ts` checks them and names the
  failed one in `deny`; `access_test.rego` holds it under `opa test`. One
  divergence from the sketch: an absent grants field is an empty set, so an
  actor with no grants is denied and told why rather than denied silently.
- **The release gate counts the definition of inception completion.**
  `npm run release:report` blocks on every unverified journey, every adapter
  without sandbox verification and every evidence-pack artifact nothing
  produces, and `generated/INCEPTION-COVERAGE.md` prints the same figures
  (0 of 17 scopes deployed, 1 of 75 routes contracted, 0 of 24 journeys
  verified, 0 of 13 adapters sandbox-verified, 0 of 27 artifacts present).

Not done: no operating system is implemented, deployed or activated by this
decision; 23 of the 24 journeys have no code path; the proposed events need
catalog entries in the same change as their first consumer (ADR 0008); the
SQL suite was run on PostgreSQL 16 locally and only CI has proved it on 17.
