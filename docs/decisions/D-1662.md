## D-1662 · A grade release reaches the student's Action Center through a per-consumer relay on the existing outbox

**Decided 2026-10-20.** Builds on [`D-1475`](D-1475.md) §13, which made
`gradebook_release` emit `gradebook.grades_released` v1 in its own transaction.

**What.** `20261022090000_grade_release_student_actions.sql` adds the event's
first consumer. `private.claim_grade_release_events` claims only that type and
version. `private.apply_grade_release_event` writes one
`public.student_actions` row per grade version the release wrote, then the
`student_actions` watermark and the consumer's receipt, all in one transaction.
`public.run_student_action_relay(25)` is the service-only tick. The student reads
their rows through `my_student_actions()` and moves one through
`settle_student_action(id, state, version, key)`. The app ranks these rows in
the existing Action Center (`lib/student-actions*.ts`, `TodayActionCenter`).

**Reused, not rebuilt.** The outbox (`domain_outbox_events`), the per-consumer
receipts (`domain_event_receipts`), the read-model registry and watermark,
`fail_domain_event`'s retry rule, and `replay_domain_event`'s approval
(`projection-replay`, two-person), MFA and audit path. No event type,
capability, Edge Function or scheduler is added.

**Why per-consumer delivery state.** The outbox's lease and outcome columns
are on the event row, so they are global to the event. Receipts are per
consumer. If one subscriber settles an event through `complete_domain_event`,
the event is published, and every claim on main skips published events, so
every other subscriber stops seeing it. D-1475 names the passback queue, a
notification and a projection as consumers of this event, so a single-dispatch
owner was not assumed. Instead, `private.domain_event_deliveries`
(consumer, event) holds this consumer's lease (five minutes, skip locked),
attempts, due time, sanitized error and dead letter. The relay never writes the
event row. `replay_domain_event` and its approval trigger now accept either a
parked event or one consumer's parked delivery, and every other gate is
unchanged. `ops_projection_dashboard` reads this model's backlog and dead
letters from its own deliveries and receipts. The SQL suite has another
subscriber publish every due event through the generic claim before the relay
runs. The relay still applies them, and both receipts exist.

**Why a new table.** `institution_actions` (D-048) is office-published
content. It requires an office, an https link and a publisher, it goes through
a two-person publish, and its progress table records done only, with no
dismissed and no version. A grade release fits none of that. `student_actions`
is minimal: owner `student_id`, item, grade version, source event,
`open | done | dismissed`, a version and the last settle key. It has RLS for
own rows only and no client write grant.

**What a release resolves to.** The event names no student. The rows are the
item's `released` versions whose `operation` is the release's key, which
`gradebook_release` writes on each row and which is also the event's
idempotency key. The key is the filter that matters. Measured: with it
removed, the first release resolves to the second release's student too. The
`status = 'released'` filter is redundant with it (removing that filter leaves
the suite green) and stays as a second lock. More rows than the event's
`released` count is refused as 23514 and dead-lettered. Fewer is allowed,
because a student account deleted since the release cascades. An item that no
longer exists is settled as skipped.

**Owner decisions defaulted here, for the owner to confirm or change:**

1. **Retries and dead letter.** `fail_domain_event`'s rule is copied, not
   re-tuned: 8 attempts, 2^n seconds capped at 15 minutes plus a
   deterministic jitter under a second. SQLSTATE 22023/23514 (a malformed
   event, or a release that disagrees with its event) dead-letters on the
   first attempt. Every other error retries.
2. **Dead-letter policy.** A parked delivery stays parked and visible on the
   operations dashboard until an approved `projection-replay` resets it. Each
   replay is written to the console audit, and running the same approval
   again does nothing. Nothing expires or discards a parked delivery. It goes
   only when its event is pruned (`on delete cascade`).
3. **Scheduling.** None. `run_student_action_relay` runs only when the service
   role calls it. No cron entry, Edge Function or secret is added, and nothing
   is enabled on any project. **Merging applies the migration to the
   canonical project, but nothing will run the tick there.** Released
   feedback appears only after someone calls it. Choosing a runner (a
   scheduled Edge Function like `ops-projector`, or pg_cron) and its cadence
   is the owner's decision.
4. **What a changed grade does to an action.** The gradebook has no
   un-release: versions are append-only, and a change after release is a
   draft the student cannot read until it is released. While the change is a
   draft, the action stays in the feed, because it points at the grade the
   student is shown. When the change is released, its own action appears and
   the old one leaves the feed and can no longer be settled. The old row is
   kept, not deleted, so if the student had marked it done, the new one is
   open again.
5. **Ownership of the state.** The server owns done, dismissed and open, and
   a stale version is refused. Snooze, start and notes stay on the device like
   every other Action Center action. A dismissal reason is not sent to the
   server.
6. **Flag.** The rows are shown wherever the Action Center is shown
   (`today_action_center`, off by default). No new flag is added.

**Not done.**

- No runner or schedule, as above. Also no Edge Function wrapper.
- The single-subscriber alternative was not taken, so the event row's
  `published_at` is never set for this type. Generic outbox counts that read
  "unpublished" (the `domain_outbox_pending` index) will count released
  grades as pending forever, unless a future change marks an event published
  once every registered subscriber has a receipt.
- No `projection_invalidation` row is written: nothing reads one for this
  model yet.
- The Today shadow (`composition/shadow.ts`, off unless built with
  `VITE_TODAY_SHADOW=on`) names released feedback as its one known gap: the
  domain layer has no source for it.
- Checked on Postgres 16 only. The project runs 17, which is not installed in
  this environment.
- No screenshot. The feed needs a signed-in account against a database. The
  mounted test covers loading, empty, error, stale, Done/Undo and Bring back.
- Notifications (push or email) for released feedback are not built.
