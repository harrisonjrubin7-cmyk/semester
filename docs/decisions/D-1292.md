## D-1292 · Semester is served from one Vercel project, `semester`, with the company site as a third service

**Decided 5 October 2026.**

Three Vercel projects served Semester: `semester` (Git-linked, no custom
domain), `semester-company-site` (Git-linked, no custom domain) and
`semester-shared-core` (holds `www.semesterintel.tech`, deployed by CLI from a
commit of this repository since 1 October). The canonical one is `semester`:
it is linked to this repository's `main`, it already deploys
the `app` and `workflow-lab` services (#1288), and it has the strongest
configuration in the repository.

- The company site becomes a third service in the root `vercel.json`, selected
  by host (`semester.website`, `www.semester.website`), so its absolute asset
  paths keep working and no other host changes. No iframe, no reverse proxy.
- The two Supabase projects are **not** merged. `Semester2` is a prototype data
  set on a lineage that shares nothing with production; anything wanted from it
  is a port onto the production lineage.
- Secrets are not copied by an agent. The `MERGE` rows of
  [`VERCEL-CONSOLIDATION.md`](../infrastructure/VERCEL-CONSOLIDATION.md) §5 move
  through the dashboard or the CLI on the owner's machine.
- No project, deployment or domain is deleted. The old projects are paused,
  then archived, after a clean day on the canonical one.

**Not done:** the domain moves (§6), the secret transfer, the Supabase Auth
redirect allow-list, and `semester.website`, which is served from a Vercel
scope the audit could not see. The host rewrite is unexercised until a domain
is attached.
