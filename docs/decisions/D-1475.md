**Decided 2026-10-11**, by the assistant under the standing delegation D-1287 records; the founder can overrule any of it. None of it is a legal, financial or production step.

**2. The ecosystem coverage matrix is generated, never hand-edited.** `app/src/lib/docs/ecosystem.ts` builds `docs/ecosystem/COVERAGE-MATRIX.csv`, `docs/registry-status.json` (the Phase 0 deliverable `REPO-CROSSWALK.md` names) and the counts block of `docs/ecosystem/INVENTORY.md` from three inputs: the prototype's 281 routes, the design registry's 122 capabilities, and `docs/ecosystem/crosswalk.json`, the curated evidence per route. The test regenerates all three and fails on any difference, so the matrix cannot drift from the crosswalk. Why generated: the stream 00 audit (`docs/master/REPO_AUDIT.md`) is a document that was right on 5 October and has no way to notice when a cited file moves; this one does.

**3. The crosswalk can be refused by the tree.** Every path it cites must exist, and a status must be reachable from what is cited: `tested` needs a test, `connected` needs code, `schema-present` needs a migration. A row that over-claims is reported and the build fails. Controls in the test prove each refusal fires on a fabricated row, so an empty crosswalk cannot pass vacuously. The ladder is `REPO-CROSSWALK.md`'s seven levels, with the coverage programme's word beside each (specified, in progress, implemented, verified, deployed).

**4. Local-first persistence counts as `connected`.** Screens whose device store syncs through `app/src/lib/cloud.ts` into `public.state` and `public.courses` (guarded by `supabase/sync.check.sql`) are rated `connected`, and `tested` where a test exercises them; each such row says "via store sync" in its note so they can be downgraded in bulk if this is overruled. The alternative, counting only screens that call a server command, would rate the shipped student app `code-present` across the board, which is not what the repository's own persistence model is.

**5. Nothing is `deployed` until the running app has been seen.** `deployed.json` records what this session could establish: the production project `lzrqvlugnawcgywkhqlz` lists 234 migration versions whose md5 over the ordered list equals the digest of the repository's 234 file names, read with a read-only query and nothing applied. The Vercel deployment listing refused this session's credentials and the production URL is a repository variable not readable here, so `app.verified` is `false` and the test asserts no row reaches `deployed` while it is. A green build is not a deployment; the matrix says so in every row that has code.

**12. The onboarding step is persisted.** `state.onb` moves from the ephemeral half to the persisted half so that an interrupted onboarding resumes where it stopped (Phase 2 hardening item 1). The Phase 2 exit gate's own IDs (S01–S04, F03–F05) remain untitled; the plan's eight hardening items and eleven closeout tests are recorded in the register as `P2-H*` and `P2-C*`, identifiers this repository made up and says so.

**13. A grade release and its outbox event are one transaction.** `20261012010000_gradebook_release_emits_event.sql` makes `gradebook_release` emit `gradebook.grades_released` through `private.emit_domain_event` before returning, keyed by the release key, with the item and counts and no student in the payload. The ledger accepts a key of 8 to 200 characters and the outbox a correlation id of 8 to 128, so a key longer than 128 rides whole as the idempotency key (300 allowed) and is correlated by `gb:` plus its md5; copying it, as the first cut did, made a contract-valid key abort the whole release (found by the Vercel Agent review on `53c8ecfd`, reproduced by `gradebook.check.sql`, which now releases with a 200-character key). The passback queue stays a separate call; what changes is that a release can no longer commit silently. This is the first migration this pull request adds; it is applied by CI to the throwaway database and is not applied to production here.

**15. Authority handed out or kept without the server's record is closed in one migration.** `20261012050000_provisioning_authority_hardening.sql` does three things the Phase 4 audits found open. The identity-provider group → role mapping (`scim_group_mapping`), which decides who becomes `admin` at a school, had a client-written approver and no history; its approver and time are now stamped from the session and every insert or update is copied to an immutable `scim_group_mapping_history` readable with `audit:read`. Integration approval had no way back: `integration_revoke_connection` and `integration_revoke_scope` take the same `integration:approve` capability the approval took, need a reason, clear the approval and disconnect, so the worker's existing rule refuses the next run; scopes carry a server-stamped `proposed_by` (the client cannot write it: the column is outside the insert grant) and the proposer cannot approve. A membership deprovisioned by the identity provider now also ends the person's `auth.sessions`, the way school offboarding does for a whole school; the session ends everywhere, not only at the deprovisioning school, because signing in again is the one path that re-checks every membership, and a token that outlived its membership kept working against PostgREST until it expired. Each is proven in the suite that owned the gap (`identity-provisioning` 19 → 38 checks, `integration-control-plane` 76 → 96, `offboarding-grants` 13 → 15), each watched red before the migration existed. The first cut's history trigger refused every update and delete, the foreign keys' included, so erasing an administrator's account failed on `changed_by`'s `set null`; it now admits that one edit (the pattern `20260930233000` uses for guardian history), and the identical fault in `tenant_sso_policy_history` from `20260928011845` is corrected alongside. The stamp trigger leaves the approval time alone when the key clears the approver, and the history records the erasure as a change with no author. This is the second migration this pull request adds; CI applies it to the throwaway database and it is not applied to production here.
