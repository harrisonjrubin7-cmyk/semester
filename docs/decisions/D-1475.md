## D-1475 · The coverage matrix is generated from a crosswalk the tree can refuse, and nothing is called deployed until the running app has been seen

**Decided 2026-10-11**, by the assistant under the standing delegation D-1287 records; the founder can overrule any of it. None of it is a legal, financial or production step.

**1. The 11 October design export joins `docs/handoff/` on D-1287's terms.** 445 non-PDF files added and 8 updated; the 61 PDFs (27.6 MB) stay out, as the first export's did, and most have a `.txt` twin beside them in the archive. The export was scanned for key material before intake and none was found. The interactive prototype (`ui_kits/`) was not in this archive either, so `prototype/screens.json` and `SCREEN-INVENTORY.md` are the acceptance list until the founder supplies it.

**2. The ecosystem coverage matrix is generated, never hand-edited.** `app/src/lib/docs/ecosystem.ts` builds `docs/ecosystem/COVERAGE-MATRIX.csv`, `docs/registry-status.json` (the Phase 0 deliverable `REPO-CROSSWALK.md` names) and the counts block of `docs/ecosystem/INVENTORY.md` from three inputs: the prototype's 281 routes, the design registry's 122 capabilities, and `docs/ecosystem/crosswalk.json`, the curated evidence per route. The test regenerates all three and fails on any difference, so the matrix cannot drift from the crosswalk. Why generated: the stream 00 audit (`docs/master/REPO_AUDIT.md`) is a document that was right on 5 October and has no way to notice when a cited file moves; this one does.

**3. The crosswalk can be refused by the tree.** Every path it cites must exist, and a status must be reachable from what is cited: `tested` needs a test, `connected` needs code, `schema-present` needs a migration. A row that over-claims is reported and the build fails. Controls in the test prove each refusal fires on a fabricated row, so an empty crosswalk cannot pass vacuously. The ladder is `REPO-CROSSWALK.md`'s seven levels, with the coverage programme's word beside each (specified, in progress, implemented, verified, deployed).

**4. Local-first persistence counts as `connected`.** Screens whose device store syncs through `app/src/lib/cloud.ts` into `public.state` and `public.courses` (guarded by `supabase/sync.check.sql`) are rated `connected`, and `tested` where a test exercises them; each such row says "via store sync" in its note so they can be downgraded in bulk if this is overruled. The alternative, counting only screens that call a server command, would rate the shipped student app `code-present` across the board, which is not what the repository's own persistence model is.

**5. Nothing is `deployed` until the running app has been seen.** `deployed.json` records what this session could establish: the production project `lzrqvlugnawcgywkhqlz` lists 234 migration versions whose md5 over the ordered list equals the digest of the repository's 234 file names, read with a read-only query and nothing applied. The Vercel deployment listing refused this session's credentials and the production URL is a repository variable not readable here, so `app.verified` is `false` and the test asserts no row reaches `deployed` while it is. A green build is not a deployment; the matrix says so in every row that has code.

**6. Capability links are curated by hand and a capability takes the lowest status of its routes.** The registry's design-side routes (`/app/courses`) do not name prototype routes (`#/student/courses`), so the link is a table in `crosswalk.json`. A capability carried by nothing is `specified` and says so.

**7. The repository's `/simplify` skill was not run before this commit.** The session's tooling asks for it before every commit; in this repository it is the screen-consolidation programme recorded in `SIMPLIFY-AUDIT.md`, which this change does not touch and which would widen the pull request past what was asked.
