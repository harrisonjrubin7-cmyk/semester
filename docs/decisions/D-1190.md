## D-1190 · Personal tasks are the first thing carried through the sync engine, over the existing table, behind a device-local opt-in

**Decided 2026-10-04.** Builds on D-1162. The slice is [`app/src/lib/sync/engine/`](../../app/src/lib/sync/engine) and §10a of [`mobile-offline-reference.md`](../architecture/mobile-offline-reference.md).

- **Tasks only, over `public.tasks`, no migration.** The table, its row-level security, its tombstone and its `updated_at` trigger already exist and are unused. A new receipts table or definer function would ship without a Postgres 17 check run, which this environment cannot do, so the interim transport keeps its idempotency key in the row (`data._cmd`) and orders by arrival. Both limits are written down; neither is the gateway's guarantee.
- **One owner, one-way mirror.** While a device has opted in, the engine is the single source of its tasks and the old sync half neither reads the blob's tasks back nor counts them in its base. What the device pushes still carries them so devices that have not opted in keep receiving them. The cost is accepted and stated: edits made to tasks on a device that has not opted in do not reach an opted-in one, so opt in on every device of an account.
- **A registered module flag and a device opt-in; both required.** `offline_engine_tasks` (`VITE_OFFLINE_ENGINE_TASKS`) is a module flag, not a `FLAGS` entry: `FLAGS` is evaluated per school through `feature_state`, and this is a personal feature with no school. Its owner, rollout, success criteria, rollback and review date are in `docs/FEATURE-FLAG-REGISTRY.md`. The flag decides whether a build has the feature; the device's own opt-in (`semester.engine.tasks = on`, cleared by Erase from this device) is the per-device consent the one-way mirror calls for. It has no database kill switch: a new `kill.*` key needs a migration this environment cannot check, and the rollback does not need one — set the variable to `off` and every device returns to the account sync with no task lost, because the old half has pushed the task list all along. The one thing that can come back is a task deleted while the engine was on, on a device that had not opted in.
- **The student's edit wins a race with the engine.** The engine's copy of a task replaces the list's only if the student has not changed it since it was adopted.
- **The sync line never says "Synced" over work the account has not confirmed**, and says refused actions are still saved on the device. The product's word is "action".
- **Interim, and superseded by D-1175 once it is mounted.** D-1175 specifies the same ideas as a service (client-minted command id, compare-and-swap, a ledger, a hybrid clock, a cursor) but mounts nothing: no route, authenticator or Postgres adapter exists, and `public.tasks` is still the only table a real device can reach. This transport is therefore the one that works today, off by default. It differs from D-1175 in a 30-day command lifetime kept in the engine rather than the server, no ledger beyond `data._cmd`, an 80-day cursor horizon, and per-row compare-and-swap rather than a batch. When D-1175 is mounted the engine's transport moves to it behind the same `SyncTransport` port and this one is retired; the engine, store and UI do not change.

Not decided and not done: the rollout itself; a screen for task conflicts and rejections and per-task labels; notes, appointments and practice papers; the gateway, receipts table and permission epoch; any native client. The capability registry rows stay Absent. No legal conclusion is made here.
