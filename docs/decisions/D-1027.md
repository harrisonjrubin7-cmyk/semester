## D-1027 · Decisions take their pull request's number, a change owed at reload is journaled, and a push sends only the courses that changed

**Decided 30 Sep 2026.** Three of the four items the load work of D-154 left
open, and the fourth measured.

- **Decision numbers.** The log numbered decisions in turn and collided every
  time two pull requests were open at once: five renumbers in one day, nine
  for one pull request. From here a decision is `docs/decisions/D-<pull
  request number>.md`. The number is unique and known when the pull request
  opens, and the file touches no line anyone else edits. The log keeps D-001
  to D-160 (D-156, D-157 and D-160 landed from #1020, #1017 and #1030 while
  this was open) and takes no more. `lib/ops/decisionlog.test.ts` holds it,
  and the four tests that check a register's `decisions` exist read both
  places.
- **A change made just before a reload.** `flushOnLeave` starts an IndexedDB
  write the browser can abort as the document goes, so an edit made in the
  last moment was sometimes lost, and the golden path failed on it now and
  then in CI. Leaving now also writes what is owed, pending or in flight, to
  `localStorage`, which is synchronous and cannot be torn down half way. The
  next load writes it to the database before reading, and drops it only once
  that write lands. A later write that lands drops it too, so it is never
  replayed over something newer, and erasing drops it. A write started
  while another was in flight carries only the diff from that one, so its
  landing confirms nothing unless it was built on what the database is known
  to hold (found by review: the first aborted, the second landed, and the
  journal went with the first change still missing).
  `state/persist/leaving.test.ts`; removing the journal fails 4 of its 7
  tests, removing the drop-on-landing fails 1, and confirming without that
  check fails 1.
- **A push sends only the courses that changed.** Every push rewrote every
  course, and that was the first thing to give under load. `push` now skips a
  course whose data is what the database last confirmed at the stamp the push
  names, and carries the stamp forward. The stamp check is what makes it
  safe: a row changed elsewhere is written by compare-and-swap as before, and
  a skipped row is not written at all while the state row's compare-and-swap
  refuses the push. On one machine, the same run: 217 pushes a second, p95
  167 ms, before; 530 a second, p95 57 ms, after. The harness's push
  scenario is now the state row and one course, with a budget of 1,000 ms.
  The first push after a reload still sends everything, because what was
  confirmed is kept in memory until the pull on open refills it.
- **Load in front of the database.** `supabase/load/edge/` drives GoTrue,
  PostgREST and an edge function (the calendar feed) on a preview branch. It
  refuses production's URL. **It has not been run.** This pull request
  changes no migration or function, so Supabase made no preview branch for
  it, and creating one through the API timed out twice on 30 September
  without making anything. Running it on another pull request's branch would
  load and seed that branch under its author, so it was not done. It needs a
  branch made for it and whoever owns the bill to say so; the steps are at
  the top of `edge.mjs`.

**Not done.** Required status checks are strict, so a pull request reruns CI
whenever main moves; that is a repository setting, for its owner. The
capacity figures of D-154 have not been re-read since the push changed. The
edge run is from one machine and one IP, which caps sign-in at GoTrue's
per-IP limit; a campus behind one NAT address shares that limit, and the
production value of it is the owner's to confirm.
