## D-993 · Assignments and submissions exist for a school that runs `lms_assignments` in Core, and only then

**Decided 1 Oct 2026 (Prompt 3 of the Core briefs; the owner asked for the
open prompts to be taken to done in order).** D-151 and D-152 made Core a
per-module, per-school setting. This is the first LMS module behind it.

- **Only in Core.** Every writer in `20261001010000_assignments.sql` refuses
  unless the school's `lms_assignments` module is Core, not frozen, and
  `kill.core_modules` is disengaged. In Connect the school's own learning
  system is the record; a row here would be a second one.
- **Who.** `assignments:author` (faculty), `assignments:extend` (faculty,
  teaching assistants), `assignments:review` (faculty, teaching assistants)
  and `assignments:submit` (the student roles, which is the roster), each held
  over `<school>/<CODE>/<TERM>` as the gradebook's are. A grant with no term
  authorises nothing.
- **The clock is the server's.** `submitted_at` is read inside the writer;
  there is no argument to pass one. Late is that instant against the due date
  the student is held to, which is their extension if they have one.
- **Rules.** Late work is refused or taken (flagged late), with an optional
  cut-off; `attempts_allowed` is enforced under an advisory lock per student
  and assignment; every writer takes an idempotency key, so a double click is
  one submission and a reused key for another request is refused.
- **Append-only, with a receipt.** Submissions, files, receipts and
  extensions are never rewritten, even by the table owner. A receipt carries a
  SHA-256 over the server time, attempt, lateness and the work's own hashes.
  It is not a grade.
- **Files** go to the private `assignment-submissions` bucket under
  `<school>/<assignment>/<student>/<name>`; Storage lets a student write only
  their own folder of a published assignment they are on the roster of, and a
  submission may name a file only if the object is there.
- **`schools.timezone`** is added (the completeness matrix asked for it when
  Core began to serve term dates), checked against the database's own list.
- **Where it shows.** An Assignments section on the Gradebook screen, not a new
  screen and not a new navigation root: the instructor's half for an author,
  the student's half for the roster, and one sentence in Connect.
- **Proof.** `supabase/assignments.check.sql`, 87 checks. Red when the Core
  requirement is removed, when the attempt limit is removed, when the late
  refusal is removed and when the roster check is removed; each restored.
- **Not done here, on purpose:** group submissions and group extensions
  (an extension is per student), virus scanning of uploads (P7), the
  instructor's grading view of a submission (the gradebook's), and anything
  that makes a student's grade from a submission: AI never decides a grade.

### Attendance (Prompt 5, first half)

`20261001020000_attendance.sql`, on the same footing: only in Core (the
`attendance` module), roster by `attendance:attend` and `attendance:take` over
`<school>/<CODE>/<TERM>`.

- **A code is a secret for one session.** Six digits, made by the server, unique
  among a school's open sessions, readable by takers and by no student. A wrong
  code is *answered*, not raised, so the try is kept; five in ten minutes stop
  that person's check-ins for the window, even with the right code. A right code
  from someone not on the course is answered as a wrong one.
- **Server clock.** Present inside the late window, late after it, refused
  outside the open window.
- **Marks are versions.** A change is a new row with who and why; the owner
  cannot rewrite one. An excused absence needs a note. Closing a session marks
  the roster's unmarked students absent, once.
- **Refused, not deferred:** location or device checks, photographs, and any
  measure of attention (the brief's "no emotion or attention monitoring").
- **Proof.** `supabase/attendance.check.sql`, 60 checks; red when the Core
  requirement, the lockout, the roster check or the late line is removed.

### Question banks and timed tests (Prompt 5, second half)

`20261001030000_assessments.sql`, behind the `lms_assessments` module.

- **A student is never sent a key.** The keys are in `bank_items`, which only
  reviewers read. `assessment_items` returns stems and options and nothing
  else; `assessment_review` shows what was right only if the instructor chose to
  and the test has closed.
- **The clock is the server's.** `started_at` and `deadline_at` are read inside
  the writer. Past the deadline a save is *answered* `time_up` (not raised, so
  the finish is kept) and the attempt is finished as expired with what was
  saved. Starting again on any device returns the attempt in progress with the
  time that is left. A refresh of a pool is the same questions.
- **Pools** are drawn when the attempt starts and fixed on it.
- **Extra time** is an explicit per-student, per-test percent with a short
  reason that is not a diagnosis; `accommodation_passports` holds a functional
  summary in words and is never read here.
- **Scoring** is the instructor's key applied by rule: a choice, a set, true or
  false, a number within a tolerance, a text after trimming and case-folding. An
  essay is not scored and flags the attempt `needs_review`. The score is a figure
  on the attempt, not a grade: nothing here writes the gradebook, and AI decides
  nothing.
- **Never rewritten:** finished attempts and their answers, extra time, and bank
  items (retired by a stamp). The guards allow only clearing the author's name
  when that person's account is deleted; the check suites for assignments and
  attendance now delete the staff who wrote a row, which found the same flaw in
  both earlier guards, fixed here.
- **Refused, not deferred:** biometric proctoring, and any emotion or attention
  monitoring. Nothing records where a student looked or which window they were
  in.
- **Proof.** `supabase/assessments.check.sql`, 108 checks; red when the Core
  requirement is removed, when a key reaches the student, when the server
  deadline is ignored, and when the numeric tolerance is ignored.
- **Not done:** QTI 3 import and export (next), and writing a test score to the
  gradebook (an instructor releases a grade in the gradebook, by hand).

### The degree audit (Prompt 9) — `20261001040000_degree_audit.sql`

- **A catalog year is a record.** A program's requirements per catalog year are
  a draft until a registrar publishes them, and are never edited after: the
  version, its groups and its rules refuse a change by trigger, and a correction
  is a new version. A student is held to a published year only; a change is a
  new declaration and the history stays.
- **The record is the ledger's.** The engine reads `academic_record_entries` as
  of today: the latest graded attempt per course, the credit entry the course
  carries, transfer credit with no grade points. A missing credit entry is said
  in the result and counts for nothing; it is never guessed.
- **Greedy, and said so.** A course counts once, in the first group it fits.
  An advisor's substitution is the way to put a course somewhere else. A group
  is `all` (one distinct course per rule), `n_of` or `credits`; a rule is a
  course or a subject with an optional number range. The result cites the
  courses behind every line and lists what counted nowhere.
- **Exceptions are two-person.** A waiver or substitution is proposed by one
  `degree:propose` holder and decided by a different `degree:approve` holder; the
  proposer cannot decide their own, and a decision is never rewritten. A
  proposal changes nothing; a rejected one changes nothing; an approved
  substitution adds its credits to the total.
- **Saved runs and what-ifs.** A saved run keeps the result, the version and a
  SHA-256 of the ledger rows read; it is never rewritten. A run against another
  year is a what-if: computed and refused if asked to save. A student may run
  their own audit and cannot save one.
- **Not the Path Snapshot.** `lib/degree.ts` stays a planning estimate, labelled
  as one; nothing here reads or changes it. The UI is a tab on that screen that
  appears only for a signed-in school account and says the school's own audit
  is the record while the school is in Connect.
- **Refused, not deferred:** prerequisite checking, course availability, and any
  prediction of whether a student will graduate. AI decides nothing here.
- **Proof.** `supabase/degree_audit.check.sql`, 85 checks; red when the
  proposer-decides rule, the published-year guard (versions and rules), the
  once-only course use or the what-if save refusal is removed.
- **Not done:** program-level rules beyond groups (cross-listing, residency,
  concentrations) and an audit of a minor alongside a major in one view.

### Records and transcripts (Prompt 10) — `20261001050000_records_transcripts.sql`

- **Final grades arrive by two hands.** An instructor holding `grades:release`
  over the course and term posts final grades (the Records tab prefills the
  letter from the released gradebook under their scheme and lets them change it);
  nothing reaches the record from that. A registrar holding `records:accept`
  turns the posts into ledger *proposals* (grade and credit); the ledger's own
  rule then applies: someone else approves, and correcting a grade already on the
  record is a registrar override. A student with no record link is skipped and
  said so, never guessed. A correction before acceptance is a new version; after
  acceptance it is refused and goes to the registrar.
- **A document is a record.** `record_document_issue` snapshots the ledger as of
  today into a transcript or an enrollment letter, hashes the canonical JSON
  (SHA-256) and signs it (HMAC-SHA256 under a per-school key in `private`, which
  no client role can read). The row is never rewritten; revoking is a separate
  record; a code opens the document for 180 days. A rewritten document is
  *noticed even when its hash is made to match*, because the signature covers the
  hash and the key is not in the row; a test does exactly that. Every opening, and
  every failed one, is kept.
- **Disclosure.** Issuing to anyone but the student writes a disclosure in the same
  transaction, with the exception relied on, a basis, and for written consent the
  consent's reference. `record_disclosure_log` records a release made outside
  Semester. The student reads their own log.
- **Graduation clearance** reads, it does not decide: a saved degree audit that is
  complete *and fresh against the ledger* (the fingerprint must match), no change
  or exception waiting, no open hold, and a linked account to check holds against.
  Conferral is still proposed and approved on the ledger by two people.
- **Not done, and one decision for the owner.** The verification URL needs a
  public endpoint. This repository holds that no function in `public` is callable
  signed out, so `record_document_verify` is granted to the service role alone,
  and a public Edge Function in front of it would be the first addition to the
  pinned list of public functions (`edgeguards.test.ts` pins it to `lead-intake`).
  That is a change to a security guard and is not made here. Until the owner
  decides, the document shows its code and hash and the school confirms them. Also
  not done: the signing key lives in the database (an external KMS key is the
  stronger setting; the ledger hash chain is the other half), the PDF is the
  browser's print of the signed content, and credential networks (Clearinghouse,
  Parchment) are not connected.
- **Proof.** `supabase/records.check.sql`, 115 checks; red when the accept
  capability, the signature check, the disclosure write, the stale-audit check, the
  Core requirement or the service-role-only grant is removed. Writing it found a
  real defect in the degree audit: deleting the registrar who published a catalog
  year was refused by its own guard. Fixed in `20261001040000_degree_audit.sql`,
  with a check in the degree suite, red-then-green.

### Admissions (Prompt 11, first part) — `20261001060000_admissions.sql`

- **An applicant is an account before it is a student.** Any signed-in account
  starts one application in an open cycle (by the cycle's id, which the school
  hands out) and reads and writes only its own. Two new roles hold the office:
  `admissions_officer` (configure, review, mark documents, record a deposit) and
  `admissions_director` (decide, release).
- **Fixed when it opens.** A cycle is a draft until opened; opening freezes its
  questions and document checklist, so every applicant answered the same ones. A
  submitted application is frozen to everyone, including the owner of the data;
  the only thing it can still do is be withdrawn.
- **A person decides every admission, by two hands.** A decision is recorded by an
  `admissions:decide` holder, only on a submitted application, only after a review
  by *someone other than the decider*, only when every required document is
  received or waived, and never on the decider's own application (the director who
  also applies is a test). It is never rewritten; there is no score, ranking or
  model-written decision or summary anywhere in the module.
- **Private until released.** `admissions_release` publishes a cycle's decisions
  together; before that the applicant reads nothing about theirs, and reviewers'
  notes are never the applicant's. Only an `admit` is answered, once; a deposit
  follows an acceptance, once, by reference. History is an append-only event log
  the applicant reads without the review and decision steps.
- **Account deletion.** The application goes with the applicant's account, with
  its events, documents, reviews, decision, answer and deposit; staff names are
  cleared when staff accounts are deleted. A school that must keep a decided
  application keeps it in its own system. `lti_account_untouched` counts an
  application.
- **Found while writing the suite.** The cycle's read policy compared a bare `id`
  inside a subquery, which resolved to the application's id, so an applicant could
  never read their own cycle; qualified, with a check, red-then-green.
- **Not done.** File upload for documents (a checklist item is promised by the
  applicant and received by an officer; files follow the assignments storage
  pattern), a dedicated applicant screen and navigation root (the portal is a tab
  on the Gradebook screen today; the information architecture is the owner's call),
  application fees, and the hand-off from an accepted, deposited applicant to a
  student record.
- **Proof.** `supabase/admissions.check.sql`, 105 checks; red when the
  other-reviewer rule, the own-application rule, the required-documents rule, the
  release gate, reviewer privacy, the submitted freeze, the cycle read policy or
  the Core requirement is removed.
