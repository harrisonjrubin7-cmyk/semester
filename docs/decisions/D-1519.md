## D-1519 · A device that only syncs cannot delete what it could not read, or drop what it does not know

**Decided 12 Oct 2026.** Two ways a device that did nothing but sync could erase account data, raised by Codex on #1501. Neither was specific to repairs.

- **What was decided: rows lost on load are not deletions.**
  - The two boot readers (`loadPersisted`, and `load` in `state/persist`) note in `semester.ingress-drops` which `DELETABLE` lists lost rows, or hold rows with no id.
  - While the note is set, the next pull is taken even when the account has not moved.
  - `settleDeletions` and `coursesDeletedHere` read nothing in those lists as deleted here, so the union merge puts the account's copies back before the first push.
  - The note is cleared after that pull lands.
  - The hold lasts only for that healing pull. A stray id-less row left in a list does not stop later deletions: keyed to the row, one loose row would have stopped every deletion in the list for good (Codex on 60dd44c).
  - The note is also kept in memory, so storage at its quota cannot leave this session's pull without it. A clear whose removal storage refuses marks the stored note stale for the session, so it is not counted again (Codex on df5dd87).
  - A row with a blank id, or the same id as another row, counts as lost: it cannot say which agreed id it was (Codex on bffd8da).
  - A list stored as something other than a list counts as lost whole: the reader makes it empty, and pushed as it is that empties the account's list (Codex on c798527).
  - `forgetSyncMemory` clears the note in memory as well as in storage, so an account switch does not hold back the next account's deletions (Codex on c798527).
  - The note goes only once the healed copy is durable: at once on the database path, which already waited for the write; without a database, after the save that follows succeeds. A save refused for room keeps it (Codex on c714dc3). A heal that changed nothing clears it against what storage last accepted (Codex on afe376f).
  - Merging or taking the account copy at the first-sign-in or account-switch question clears it too (Codex on c714dc3).
  - A note localStorage refused rides on the saved copy itself (`heldIngressDrops`), so a close before the pull cannot leave the gap with no note: inside the localStorage text without a database (Codex on 36c7453), and as a settings row in the same database write with one, the move off localStorage included (Codex on 301db55 and 3615f39). The row counts as written only once its write has landed, and a tab drops a note the database carried once another tab's heal has removed it (Codex on 3615f39). The reader takes it out of the state, and the heal takes it off the saved copy.
  - A tab whose note reached storage lets go of it once another tab's heal has removed it (Codex on 36c7453).
- **Why the note is kept in storage rather than in memory.** The drop happens once. The next save writes the list without the row, and the boot after that sees nothing missing. A device that closes before it syncs must still know, on the next boot, that the gap is damage.
- **Why hold the whole list rather than one id.** A row that lost its id cannot say which agreed id it was. Holding the list costs at most a deletion made in the same window coming back, which is visible and can be done again. Guessing wrong deletes the account's good copy.
- **Why force a take.** With the account unchanged, the store did not pull into this device, so no settle ran and the next push wrote the gap over the account. Pushes already wait for a successful pull (`pushReady`), so a forced take always lands before them.
- **What was decided: fields from a newer build go back up.**
  - `lib/carried.ts` keeps, per account, the last pull's top-level fields that this build does not know (`DEFAULT_PERSISTED` plus `courses`).
  - `push` puts them back on the way up, and the outgoing copy wins any key it holds.
  - The copy read from the newer account version wins, by the state row's `updated_at`, which only the database sets, compared to the microsecond the database keeps: this session's memory over a stored copy a refused write left behind, and a copy another open tab stored from a newer version over this tab's memory. Not by when a pull finished, since a slow pull of an older version can land last, and an older pull never overwrites a newer stored copy. An empty result is stored too, so other tabs learn a field is gone (Codex on c714dc3, bffd8da and afe376f). A stored copy outranks memory only for the same account (Codex on df5dd87).
  - What is stored is everything beyond `CARRIED_BASELINE`, the fields this build persists, written out so the set does not grow with later builds. Each reader puts back only what it does not know. Storing "what the writer does not know" let a newer tab's copy, which left out a field it knew, win in an older tab that then pushed without it (Codex on 36c7453).
  - A push that lands replaces the carried copy with what it sent, at the version it made, so an older build's tab never sends the fields of the pull before it (Codex on 746bbbd).
  - `forgetSyncMemory` forgets them, and so does choosing "Use this device" at the first-sign-in or account-switch question, whose push replaces the account (Codex on 301db55).
- **Why only unknown keys.** A known key left out of a push was left out on purpose. Carrying it would resurrect what this build decided not to send. The cost is that a field a later build retires is carried until every device drops it, which is harmless.
- **Held by.**
  - `lib/deletions.test.ts`: thirteen tests under *rows lost on the way in*.
  - `lib/conflicts.test.ts`: `forgetSyncMemory` clears the in-memory note.
  - `lib/carried.test.ts`: sixteen tests, six of them with a second tab.
  - `state/persist/ingress.test.ts`: the database boot path, with a control that notes nothing, and the note carried in the database write, read back, and released after a heal.
  - Fourteen store journeys in `state/syncstates.test.tsx`, including a refused save and a refused note without a database, each with a control.
  - Each guard was reverted and watched fail: the forced take, the settle parameter, each boot path's noting, and the carried push.
- **Not done.**
  - A build that predates this one still drops fields it does not know. Only the database can refuse such a write: a guard on the `state` row against lowering `schemaVersion` or dropping keys. That is a migration on the hosted project and waits for the owner's approval.
  - Nothing tells the student that a list was held back.
  - A row that lost its id is kept, as the list reader always keeps it, so every boot notes its list again and holds it for that session's first pull: a deletion made offline before that pull comes back, visibly, and can be made again (Codex on 3615f39). Ending that means changing the student's row, by giving it an id or removing it, and that is the owner's call.
