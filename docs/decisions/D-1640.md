## D-1640 · The first student–faculty workflow is a library slice, not a mounted route

**Decided 2026-10-18.**

The assignment submission workflow (draft, submit with receipt, faculty assessment, released feedback) is built as command logic in `packages/institution/src/assignment-submission.ts`, with its own tests. It is not yet mounted: no gateway route, worker, migration or screen imports it.

Why:

- The repository had no submission workflow at all, and the specification asks for one completed slice with durable receipts and negative authorization tests before any broader authority is granted.
- Domain rules are testable without transport, which the specification requires. Keeping the first slice in the library lets its rules be checked before any database or route decision is made.
- It reuses the existing `ASSESSMENT_SUBMISSION` workflow, the event registry and the `Refusal` type rather than adding new ones.

Consequences:

- The event census in `platform-reference.test.ts` and `examples.test.ts` now lists the module as a producer. `docs/reference/EVENTS.md` is regenerated.
- The census mount rule now matches the producer file for `packages/institution`, because the package name was shared by the app's own server folder.

Not done, and required before mounting:

- A PIA row in `app/src/lib/governance/pia.ts` for the data this holds.
- A migration with composite tenant keys and row-level security, and a Postgres adapter.
- A named owner for the capability, and a decision on the event name `learning.submission.received.v1`, which the specification proposes and the registry does not have.
- A publisher for the outbox. Nothing calls `drainOutbox` today.
