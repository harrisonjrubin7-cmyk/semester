## D-1149 · Modularize the monolith into domains behind ports; extract no service until a named trigger fires

**Decided 2026-10-04.** Semester stays one deployable (static SPA, Supabase, edge functions, institution gateway) and is reorganised inside that deployable into bounded domains under `app/src/domains/`. Each domain is pure, speaks one `Result`/`AppError` model, is reached only through its `index.ts`, and touches legacy code only through an `acl.ts`. The module graph and the rules that hold it are in [`docs/architecture/modular-monolith.md`](../architecture/modular-monolith.md) and `app/src/domains/architecture.test.ts`. No domain is extracted into a separate service. The legacy `lib/`, `state/` and `screens/` are retired one capability at a time behind a flag, never by rewrite.

**Relation to [D-1144](D-1144.md).** D-1144 proposes a container-hosted `core` and says it tests ADR 0003; this decision does not decide that. It concerns the code inside the app, which D-1144's own conversion plan (§1 steps 2 to 4: extract pure domain, contract, shadow then switch) also begins with. The two agree on strategy and differ on location and rollout mechanism; the differences are listed in the plan.

### Why modularize rather than extract

The measured problem is coupling inside one process, which a network boundary does not fix. `state/store.tsx` has a fan-in of 338 files and `state/shape.ts` is a 2,829-line state and 284-action union. 317 files call `useStore()`. `screens/Today.tsx` has 65 imports. 194 files read the wall clock. Splitting these across a wire would keep the coupling and add latency, partial failure and a second deploy.

The product also constrains the choice. The app must stay fully usable signed out and offline (ADR 0001), the client holds only a publishable key and RLS is the authorization boundary (ADR 0002), and ADR 0003 records that there is no application server. Today, tasks and calendar are local-first, so the client is where their rules have to run today; a service split would contradict ADR 0003 (unless D-1144's proposal to test it is accepted) without any need that today's load shows.

### What would change this

A domain is extracted only when one of these is true and measured, not argued:

1. **Independent scaling.** The domain's load, not the app's, needs capacity the edge functions cannot give it (the AI gateway is the likely first case).
2. **Independent trust.** It must run where the student's device and the institution cannot alter it: grade passback, records, billing. These already sit server-side (`app/server/institution`, `supabase/functions/billing-*`).
3. **Independent release.** Two teams need to ship it on different cadences and the in-repo boundary has demonstrably not been enough.
4. **Foreign write authority.** An institution's system of record, not Semester, owns the data (D-1067's gradebook cutover).

When one fires, the seam already exists: the port a use case takes becomes a remote adapter, and callers change nothing. That is why ports are asynchronous even where the legacy store is not.

### What is not done

No screen calls a domain yet. The slice (identity, policy, tasks, calendar, Today) runs beside the legacy code and is proven against the real reducer. Moving `screens/Today.tsx` onto it behind a flag is step 4 of the sequence. The five ratchets in `legacy-baseline.json` list today's violations; they may shrink and may not grow.
