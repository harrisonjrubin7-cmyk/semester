## D-1159 · Data-backed screens answer to one typed read envelope; the notifications feed is the first, and says it is derived

**Decided 4 Oct 2026.** `docs/architecture/frontend-backend-contracts.md` and `universal-state-model.md` both named a typed state contract as unbuilt "Phase B". It is now `ReadEnvelope` / `OperationalState` in `app/src/lib/read/envelope.ts`, drawn by `components/unity/ReadState.tsx` from the state components the app already had.

- **The frontend does not infer authority.** An unknown state is `unavailable`; a read the caller may not make drops its data; `verified` needs a verifier time and an authority that can verify, so a device-derived or student-entered fact can never be `verified`; unknown freshness is `stale`, not current.
- **Notifications is the first screen on it,** replacing four fixed demo lines about courses the student might not be in. It lists the reminders the device fires, from one function (`state/reminders.ts`) shared with the firing path, labelled `estimated` with authority `derived`. "Clear all" (a global flag that hid the screen indefinitely) is replaced by per-item put-away, keyed by per-day reminder ids.
- **Not decided here:** per-role shells (the role launch register has none approved), visual-regression tooling and baseline storage, and remote telemetry. All are marked planned in `docs/architecture/frontend-architecture.md`, with no tool chosen.
- **Not done:** Today, tasks and calendar are not yet on envelopes; no server-owned notification feed exists.
