## D-1448 · An advisor writes check-ins only on a share the student made, and only while it is live

**Decided 11 October 2026.**

The workflow catalog's advising journey asks for check-ins and a success plan
the student can see (Advising #5 and #6, P0). Two ways to build it were
open: a staff caseload store, where an advisor holds a list of students and
writes to any of them, or a reply on the advisor-share grant that already
exists (D-016).

This builds the reply. `public.advisor_check_ins`
(`supabase/migrations/20261011170000_advisor_check_ins.sql`) holds a note and
up to five next steps against one `advisor_shares` row:

- **Writing.** Only `record_advisor_check_in` writes, and it refuses unless the
  caller is the share's advisor, the share is neither revoked nor expired, and
  the advisor still holds a live `academic_advisor` grant at the share's school.
  This is the gate `read_advisor_share` already uses, moved into one private
  function (`private.live_share_for_advisor`) that both new functions call.
- **Retrying.** Each draft carries a key, unique per share. A second send with
  the same key returns the first check-in and writes nothing, so a double
  submit or a lost response cannot make two.
- **Reading.** The student reads every check-in on their own shares from the
  table; the advisor reads back only through `list_share_check_ins`, under the
  same gate. Nobody else reads them.
- **Ending.** Revoking or expiring the share stops new check-ins and leaves the
  written ones in the student's view. The student may delete any check-in;
  deleting the share deletes its check-ins. Account erasure needs no new list:
  the rows cascade from `advisor_shares`, which `forget_my_advisor_shares()`
  removes at either end.
- **Acting on it.** On the student's side each next step has an "Add to my
  actions" button that adds an ordinary action. That action is the student's
  own from then on: deleting the check-in leaves it.

Each insert and delete reaches the common audit record as
`check_in.recorded` / `check_in.deleted`, with the share's school and never the
note.

**Why not a caseload.** A caseload is a list of students an advisor did not get
from the students. That changes who can see whom, and the build plan holds it
for decision Q1 (`docs/master/SEMESTER_ECOSYSTEM_INVENTORY.md` §12). The reply
on a share needs no such decision: every check-in exists because the student
shared first, and stops being writable the moment they revoke.

**Held by.** `supabase/advisor-checkins.check.sql` (37 checks; with the expiry
and revocation gate removed, "an expired share takes no check-in" fails);
`src/lib/advisor-checkins.test.ts`; `src/components/AdvisorCheckIns.test.tsx`
(with the retry sending a new key, the retry test fails; with the "already in
your actions" check removed, the add-once test fails).

**Not done.** No staff caseload screen, no advisor-initiated contact, no
notification to the student when a check-in arrives, and no remote migration:
the migration is in the tree and has not been applied to any hosted database.
