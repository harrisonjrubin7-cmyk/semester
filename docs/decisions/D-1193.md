## D-1193 · One lockfile at the workspace root, install from the root, and dependency overrides live in the root manifest

**Decided 2026-10-04.** `app/` is an npm workspace member beside `packages/*`. The lockfile is `package-lock.json` at the repository root and `app/package-lock.json` is gone. CI installs from the root and caches on the root lockfile. The `overrides` that pin `lodash-es` and `dompurify` are in the root `package.json`, because npm applies overrides only from the workspace root and silently ignores them in a member. This is the second step [D-1180](D-1180.md) deferred; the pnpm and Turborepo choice of P-01 stays deferred.

Why now, and what it cost to find out: the lockfile was seeded from `app/package-lock.json` rather than re-resolved, and all 291 packages kept the same version, resolved URL and integrity hash. Moving it still broke five things that nothing had flagged, each found by running the change: the ignored overrides, a root manifest with no `version` (which fails `npm sbom`), eight `packages/institution` tests importing vitest through `app/node_modules`, two preview scripts locating vite there, and a supply-chain test that counted the workspace members as third-party packages.

Consequence to know: `npm ci` run inside `app/` installs only `app/`'s dependencies and skips the `@semester/*` links. The gates still run from `app/`; the install runs from the root.

Not decided and not done: pnpm, Turborepo, module-boundary checks. Unverified until CI and the deploys run on it: the Vercel `semester` project's install against a lockfile two levels up, the Pages deploy, and Dependabot's reading of the workspace root.
