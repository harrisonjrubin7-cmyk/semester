## D-1250 · A productivity task carries what the app's task carries, and replaces its steps as a whole

**Decided 2026-10-04.** Extends D-1175. Its task had a title, notes, an instant, a priority and a course; the app's task also has a day with no time zone, free text for the time, a repeat rule, steps, and the id of the deadline a plan was made from. D-1175's validators refuse unknown keys, so a client moved onto the command API would have lost each on its first write. The task gains `dueOn`, `whenText`, `repeat`, `steps` and `plannedFrom` ([`contract.ts`](../../app/server/productivity/contract.ts), [the migration](../../supabase/migrations/20261004190000_productivity_task_carries_the_apps_task.sql)).

- **A day is not an instant.** `dueOn` is `YYYY-MM-DD` and means what a student means by "due Friday"; `dueAt` stays an instant for a deadline at a moment. A client sets either or both. Mapping a day onto an instant needs a zone and a time the student never chose, and a wrong guess moves the deadline across midnight, so neither is derived from the other. `dueOn` is authoritative for a verified task, like `dueAt`.
- **Free text stays free text.** `whenText` ("6:30 PM", "before work") is kept and shown and never parsed, as in the app, and is bounded to 40 characters.
- **A repeat rule must say when it stops.** `until` is required and unknown keys are refused, in the validator and again in the database, where the constraint is `coalesce(…, false)` because a `CHECK` passes on null. The SQL check found that hole in the first draft.
- **Steps and the repeat rule are replaced whole.** They are one field each, merged by the field's clock, so the later write wins the list. The cost is stated: two devices editing different steps of one task at nearly the same time keep one device's list, not both. The alternative, a clock per step, is a larger contract and is not made here.
- **Nothing the person wrote reaches the audit row or the outbox event.** Only the names of the changed fields do; tested.
- **Additive.** Every new column is nullable or has a default, nothing is dropped or retyped, and `public.tasks` is untouched.
- **Redefine a function from the definition that applies now.** The migration replaces `private.productivity_commit` and `private.productivity_task_json`. The first draft copied the commit function from the first migration, which would have silently dropped the held-prediction guard D-1222 added in a later one, and a text merge could not see it. The functions are now built on the latest definitions, and `schema.test.ts` holds that the commit function that applies last still carries the guard. The Postgres adapter suite (`supabase/adapter.sh`) sends the new fields through memory and a real database and requires identical records, which is what shows the read projection carries them.

Not decided and not done: **who may write here.** `productivity_task` is tenant-scoped (`tenant_id references public.schools`, an active membership), but the app calls a personal, school-less account tenant `self`, so such a person cannot write to this table at all. Whether they get a tenant, a nullable tenant, or stay on `public.tasks` is the owner's call. Also not done: mapping the app's non-UUID task ids to the UUIDs D-1175 requires; the app's `created` time (the server stamps its own); a mounted route, an authenticator and the Postgres adapter (D-1175 lists them as unwritten); a client transport for the sync engine; and any backfill from `public.tasks`, which D-1175 leaves to the owner. The SQL check passed here on Postgres 16 only, which says so on every run; the live project runs 17 and CI is the run that counts.
