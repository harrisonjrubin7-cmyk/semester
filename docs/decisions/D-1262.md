## D-1262 · The task engine's snapshot is sealed in the vault, with the plain store as its fallback and migration source

**Decided 4 October 2026.**

The engine's local state (`semester-engine`, one record per account) is the student's own task writing and their unsent edits. It is now stored through `lib/vault` as class `personal_plan` (`sealedSnapshotPort`, `app/src/lib/sync/engine/persistent.ts`). Three decisions, one change:

1. **Seal the whole snapshot, in the vault's database.** `personal_plan` is already an allowed class ("tasks, personal calendar annotations, goals"), so no new class was added. The record sits beside its key in `semester-vault`, so a browser that evicts one evicts both and a sealed record never outlives the key that opens it. Erase device already destroys that key first.
2. **Sealing must never cost an edit.** A plain snapshot is migrated once and removed only after the sealed copy reads back byte for byte. No Web Crypto, or any vault failure, writes the plain store as before: the alternative is refusing to save. A sealed record that will not open is treated as absent.
3. **No new flag.** The port is used exactly when the engine owns tasks, which is already behind `VITE_OFFLINE_ENGINE_TASKS` and the per-device opt-in (D-1190). A flag for a storage property of the same data would have added eight files, a CI workflow edit and a change record.

**Rollback, accepted.** Turning the engine off after a device has migrated returns it to the account sync; unsent offline edits on that device are the only loss, because the plain copy is gone. A reverse migration (read both, write plain) was considered and not built: it is code for a path that is off by default.

**Not done.** Tasks in the `localStorage` state blob, drafts and every other store are unchanged and unsealed. The wording stays "encrypted at rest in the browser's storage": the vault is software-keyed and does not defeat script running in the page.
