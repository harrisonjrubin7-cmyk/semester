## D-1653 · A hand-in is a fixed, versioned record on the gradebook, and a grade names the hand-in it was given on

**Decided 2026-10-19**, by the assistant implementing Slice 1 of the 19 October Claude Design handoff (`handoff/SLICE-1-PLAN.md` in that bundle: assignment → fixed submission → released grade); the founder can overrule any of it. Nothing here is applied to a hosted database.

**1. The thing handed in is its own append-only table on the gradebook, not a document store.** `20261019120000_learning_submissions.sql` adds `learning_submissions`: one row per hand-in, numbered per student and item, carrying the text and its SHA-256. No client may insert, update or delete a row; `learning_submit` is the only writer. Handing in again is the next version and never touches the last. The plan proposed a separate `productivity_document_revision` table holding a `body_ref`; there is no document store for a reference to point at, so the text lives in the row and the revision *is* the submission. A draft store, if one is built, feeds this; it does not replace it.

**2. A gradebook item is what is assigned.** Items have no separate published state: an item exists because somebody holding `grades:release` added it. So `learning_submit` accepts a hand-in on any item at the caller's school on a course and term where the caller holds the new `submissions:create` — granted to `student`, `undergraduate_student`, `graduate_student` and `transfer_student`, the roles that carry `grades:receive`, at the same per-term scope. Due dates, late marks and a closed window are not decided here.

**3. One idempotency ledger.** `learning_submit` spends its key through `private.gradebook_replay` / `_spend` under a new kind, `submit`, recording the item and the text's hash rather than the text. Same key and same text replays the receipt; same key and other text is refused.

**4. The event is the registry's, not a new one.** The hand-in emits `submission.finalized` (v1, `education_record`, `student_record`, from `packages/institution/src/events.ts`) through `private.emit_domain_event` in the same transaction. The payload is item, course, term, submission id and version — no student, no text.

**5. A grade names its hand-in by trigger, so no gradebook writer changes.** `grade_entries.submission_id` is set before insert: a version that is entered, changed or regraded binds the student's latest hand-in on that item at that moment (none for work graded on paper); moderation and release carry the previous version's forward. A later hand-in does not move a grade already given.

**6. Who reads.** The student their own hand-ins; the course's grade authors (`private.gradebook_author`) the course's. The registrar, department chairs, staff on other courses or terms, and other schools read none. `learning-submissions.check.sql` proves each, and the read and binding guards were each shown to fail against a revert.

**7. The app reads hand-ins apart from the gradebook.** `lib/gradebook/submissions.ts` is not called by `loadBook`, and a missing table or column reads as "not set up at your school yet", so a deployment ahead of the migration keeps showing grades.

**8. A hand-in is something a person did.** `lti_account_untouched` counts `learning_submissions`, as it counts a regrade request.

**Not done.** Joining this to `packages/institution/src/assignment-submission.ts`, which models the same slice in memory with assignment windows and private drafts and has no Postgres adapter. A due-date window. Rubrics and annotation. A faculty Action Center item on `submission.finalized` (nothing drains the outbox yet). Applying the migration anywhere hosted, which waits on the handoff's accepted decision to settle which Supabase project each deployment uses. The database suites ran on PostgreSQL 16; production runs 17.
