## D-1324 · The payment-rail registry and the verified-event inbox exist as inert, service-only tables, proved alone and applied by the owner

**Decided 6 Oct 2026**, as the next step of D-1319 (actions 6 and 7 of `docs/finance/NATIVE_FINANCIAL_PLATFORM.md` §14), taken on the owner's instruction to merge and continue.

- **What was decided.** Two tables join the schema through `20261006090000_payment_rails_and_event_inbox.sql`: `payment_rails` (a provider in one mode, with the capabilities Semester has wired) and `provider_event_inbox` (one row per signature-verified provider event: its id, a hash, and a minimized projection). Both are service-only (RLS on, no policy, every privilege revoked from `public`, `anon` and `authenticated`) and classified `service-only` in `database/schema/table-classification.json`. **Nothing reads or writes them**: no Edge Function, policy, scheduler job or app code.
- **Two rules built into the tables, not left to callers.** A rail holds no credential and cannot be made to: its `capabilities` column accepts only the adapter interface's own key names, so a secret cannot be stored under another. The inbox never holds a payload or a person: it keeps a hash and a bounded projection, refuses a run of 13 to 19 digits, never rewrites an identity column, moves status only along listed steps, treats `applied` as final, and is never deleted from.
- **Why never deleted.** How long a verified-event record is kept is a retention decision nobody has made; D-132 sets seven years for the financial records themselves. Keeping is the safe default and the trigger says so. Setting a period, and whether the projection counts as a financial record, is for the owner and the accountant.
- **Held by.** `supabase/payment-inbox.check.sql` (90 checks, including a control that its own "must be refused" probe fails on an allowed statement). Three planted bugs (applied not final, capability keys unrestricted, card numbers allowed) each turn it red. Run on Postgres 16 with the loud override; production runs 17.
- **Stays as it is.** `billing-webhook` is unchanged by this decision (D-1322). The checkout holds, D-146, D-1236 and D-1319 stand.

**Not decided here and not done.** Applying the migration to any database. Migrations are applied by hand until "Deploy to production" is switched on (`supabase/README.md`), and production changes need the owner's explicit confirmation per step (`OPERATIONS_RELEASE_GATES.md` §8.4); whether that switch is on is not known to this change. Using the tables: parking an invoice event that arrives before its subscription, dead-lettering, replay and a console view are separate changes, each needing the tables applied first. The retention period for the inbox. Any price, threshold, counsel decision or PCI determination.

**Update, same day.** The migration was applied to the connected Supabase project when this merged: a read-only check afterward found version `20261006090000` recorded, both tables present, row level security on, no policy, no `anon` or `authenticated` privilege and zero rows. So "Deploy to production" (`supabase/README.md`) is on for that project, and a migration merged to main reaches it without a manual step; the paragraph above that says applying it was left to the owner is superseded by that fact. What was true before the merge, and is still true, is that the owner was told this might happen and said to merge.
