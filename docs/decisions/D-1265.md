## D-1265 · The productivity service runs at `/api/productivity`, for school members only, and off until a deployment turns it on

**Decided 2026-10-04.** Extends D-1175 and D-1250, and answers the question D-1250 left open. The service, its HTTP handler and its Postgres adapter existed and nothing ran them. This mounts them: [`api/productivity/[...path].ts`](../../app/api/productivity/%5B...path%5D.ts) is the Vercel function and [`runtime.ts`](../../app/server/productivity/runtime.ts) composes the authenticator, the repository, the service and the handler.

- **A person with no school stays on `public.tasks`.** The service's tables are tenant-scoped (`tenant_id references public.schools`, an active membership), and the app calls a personal account tenant `self`, which has no school row. Giving such an account a tenant, or a nullable one, would put a hole in the isolation every other policy in this service stands on, to serve accounts whose tasks already work where they are. The route therefore has no personal-account path: the authenticator it uses resolves only an authorized SSO provider and one active membership, so a personal account gets a 401 and no principal exists to scope. Nothing was written to make this so; [`runtime.test.ts`](../../app/server/productivity/runtime.test.ts) holds that no principal is a job or carries an import capability, and that a person at another school reads an empty workspace. If school-less accounts ever need a server-side home it is a different table, decided on its own.
- **One answer to "who is this".** The authenticator is the institution gateway's: the token is validated over the network and tenant and roles are reloaded from current membership records, never read from the request or from token metadata. A tenant hint in a header is not read at all.
- **`productivity:use` is granted, not looked up.** The policy treats it as an institution capability ("planning tools at this institution") and there is no tenant capability table to read it from. Every active member of a deployment that has switched the service on gets it; the switch is the only place it is decided. A per-tenant grant replaces that one line in `principalFor`, not the policy.
- **Off unless asked.** The function answers only when a deployment sets `SEMESTER_PRODUCTIVITY` to on. Off, it returns the same 503 an unconfigured gateway does, so an unswitched deployment has no endpoint that behaves unlike a missing one. On, it refuses to start without the three auth credentials rather than starting open. Nothing in the app calls the route yet.
- **Logs carry no content.** The authorization record reuses `institution.authorization`, the same decision by the same resolver. `productivity.request` carries the route template and ids, never a path; `productivity.error` carries the error's class and ids, never its message. Both are in [`ANALYTICS-MARKS.md`](../reference/ANALYTICS-MARKS.md), with a test that holds the fields to the code.
- **Rate limits share the gateway's table under keys of their own.** Reads and writes have separate budgets (300 and 120 per window), keyed `productivity.read:` and `productivity.write:` so they cannot meet the gateway's own counter for the same person.
- **Producer guards moved with it.** The two mount probes were written to go red here and now expect exactly this route, and that it checks the switch first. The outbox still has no publisher.

Not decided and not done: the client transport (the app's non-UUID task ids to the UUIDs D-1175 requires, and the `time`, `repeat` and `steps` mapping), a per-tenant capability, and any backfill from `public.tasks`, which D-1175 leaves to the owner. Nothing has run this against a live project: it is covered by the in-memory service through the real HTTP handler and by the fail-closed configuration tests. Switching it on in a deployment is the first time the authenticator and the Postgres adapter meet.
