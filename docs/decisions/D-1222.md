## D-1222 · The Postgres repository predicts sequence numbers, re-runs on conflict, and reads only finished JSON

**Decided 2026-10-04.** The productivity repository adapter is optimistic: a transaction reads, stages every write in memory and commits once through `productivity_commit`; on `40001` or `23505` it throws the staged writes away and re-runs the work from the reads, so a decision is never made on one state and applied to another. The sequence number the service is handed before the commit allocates it is *predicted* from the owner's counter and held to by the commit, so a number returned from `save` is never one two writers both believed was theirs. Every read is a SQL function returning the entity in the service's own shape, so the adapter maps no rows and a column cannot drift from a field. See [`docs/API-PLATFORM.md`](../API-PLATFORM.md) §4.2 and §10.7.

It is held by a scripted-client suite in `npm test` and, on demand, by `supabase/adapter.sh`, which runs the same adapter and the same command script against memory and a real migrated Postgres, and races processes that share nothing. The adapter is *not* proven against PostgREST: it uses only `rpc`, JSON and SQLSTATE, and the first run against a project should confirm the SQLSTATE arrives in `error.code`.

Not decided and not done: nothing constructs the adapter and no route is mounted; the authenticator and client are unwritten; the adapter sets no timeouts of its own; contention on one owner is bounded by the retry budget and was not measured against real latency.

Added after review of the registration gap: `lti_account_untouched` now lists the two tables; export and erasure already carried them through the `auth.users` foreign keys, which the check now shows.
