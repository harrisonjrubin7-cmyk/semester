## D-1061 · A transcript is the school's ledger as of a date, in a fixed text with a SHA-256, never signed here, and every release of one is a log line nobody edits

**Decided 1 Oct 2026.** D-145 built the academic-record ledger and said plainly
that issuing a transcript was not done there. D-151 made Core a module-at-a-time
direction, and `records` is on its list. This is the next step and only that
step: a registrar issues a transcript from the ledger, anybody signed in can
check one, and every release is logged. Nothing on main issued a transcript or
logged a disclosure before this (checked by grepping migrations, `app/src/lib`
and `docs`).

- **Issuing.** `transcript:issue` (registrar) issues one for one student
  reference as of a date. The database reads the ledger as of the date (the entry
  in effect for each key, a void meaning absent), builds one canonical text and
  keeps one append-only row: a serial that rises by one for each school, the
  issuer, the date, the text and its SHA-256. A transcript is never edited. A
  correction is a new issue that names the one it replaces; a separate
  append-only row marks the earlier one superseded. Nothing is written to the
  ledger.
- **The canonical text is defined, once, in both languages.** Objects, arrays and
  strings only; keys sorted by UTF-8 bytes; strings escaped as JSON escapes them;
  no whitespace; no normalisation; the hash is SHA-256 of the UTF-8 bytes. The
  SQL function and its TypeScript twin must both reproduce one fixtures file
  exactly, including the case where byte order and JavaScript's sort differ.
- **Checking.** `transcript_verify(serial, hash)` answers valid, superseded or
  unknown with the school and the day, and never the text or the student. The
  repository's rate limit counts a hit against an account or a form and has
  nothing for a signed-out caller, so no pattern fits a public check. It is
  therefore behind sign-in and counts each call against the account, 120 an hour.
- **The disclosure log.** Every release is one append-only row: who released it,
  to whom (a name and a kind in the registrar's words, because the categories are
  a school's to choose), the purpose, the serial, when. No role updates or
  deletes one. Semester sends nothing; the row is the registrar's record that a
  release happened.
- **Reading.** `transcript:read` (registrar, dean). A student reads their own
  transcripts and the log of their own record through
  `academic_record_subjects`, and no other. No existing capability is widened.
- **Gated like every Core module.** Writing needs the school to have switched
  `records` to Core, and is refused while frozen or under `kill.core_modules`;
  every doubt reads Connect. Reading and checking are not gated by mode. No
  school has switched it.

**Not signed.** A hash shows the text has not changed since it was issued; it
does not show who issued it. Signing needs a decision about who holds a key and
what happens when it is lost, and the owner has not made it. The text carries a
sentence saying so, and the screen says it before anything else and does not use
the words official, certified or authenticated about what it shows.

**Not decided.** How long a school keeps an issued transcript, a replacement or
the log of releases: a school may be legally required to keep the log, and no
period is stated or applied. Whether a financial hold blocks a release: the
school's policy, none built. What counts as a recipient kind. Whether a
transcript of an older record should be able to carry a later date.

**Not done.** PDF rendering, a signature, delivery by email, an e-transcript
network, HEDS or PESC formats, fee collection and holds on release. Terms are in
byte order, not calendar order, because the ledger holds no calendar. A
`requirement` entry is not read. The migration is applied to no database;
applying it needs the owner's decision.
