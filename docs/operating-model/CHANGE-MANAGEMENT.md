# Change management and adoption

Adoption is a product and a service, not an email. Guidance on digital transformation follows the same arc: assess
readiness, set goals, secure buy-in across campus, implement strategically, then evaluate and adjust. The playbooks
that already exist, [IMPLEMENTATION_PLAYBOOK.md](../market-readiness/IMPLEMENTATION_PLAYBOOK.md),
[PILOT_PLAYBOOK.md](../market-readiness/PILOT_PLAYBOOK.md) and
[UNIVERSITY_ONBOARDING.md](../market-readiness/UNIVERSITY_ONBOARDING.md), carry the steps. This document adds the
stakeholder model and the adoption tools around them.

## Institutional change path

```text
Readiness assessment
→ stakeholder map
→ governance charter
→ scoped pilot (one priority workflow)
→ configuration and training
→ launch communications
→ hypercare
→ outcome review
→ expansion or revision
```

## Stakeholder change map

| Stakeholder | Change concern | Semester governance response |
| --- | --- | --- |
| Students | Privacy, complexity, usefulness | My Data controls, clear onboarding, explainable actions |
| Faculty | Workload, autonomy, AI integrity | Course-level settings, preview, source packs, no surveillance |
| Advisors | Workflow change, data quality | Agenda/scenario tools, source freshness, scoped access |
| Registrar | Accuracy, registration authority | Read-first integrations, source labels, no unauthorized write-back |
| CIO/CISO | Security, integration risk | HECVAT, SSO, RLS, audit, connector maturity |
| Accessibility office | Compliance and support | VPAT/ACR, testing, remediation workflow |
| Library | Licensed content and research integrity | Source controls, citation workflow, consultation handoffs |
| Student affairs | Community safety and engagement | Moderation, verified organizations, consent controls |
| Procurement/legal | Contract risk and vendor viability | DPA, terms, SLA, offboarding, evidence package |
| Executive sponsor | ROI and adoption | Outcome dashboard, QBR, pilot-to-expansion plan |

## Adoption tools

| Tool | Purpose | Status |
| --- | --- | --- |
| Change readiness assessment | Score readiness before scoping a pilot | Template (below) |
| Stakeholder map | The table above, filled per institution | Template |
| Governance committee workspace | Decision log and charter per institution | Process |
| Feature rollout calendar | What turns on, where and when, driven by the flag registry | Process |
| Communications templates | Course, department and campus announcements | Process |
| Training assignments and completion | Role-based training tracked to completion | Designed |
| Office hours and onboarding events | Scheduled per launch cohort | Process |
| Role-based release notes | Release notes filtered by role | Designed |
| Pilot cohort manager | Which courses, departments and students are in a cohort | Designed |
| Privacy-safe adoption heatmaps | Adoption by department, aggregate only, minimum cell size | Designed |
| Feedback triage and response status | Every piece of feedback gets a visible status | Process |
| Change-impact assessment | Required before a major policy or module change reaches a live tenant | Process |
| Campus roadmap and decision log | Shared with the institution's governance committee | Process |

## Readiness assessment (score 1–5 each)

Executive sponsor named · governance committee exists · priority workflow chosen · integration owner named · data
stewards named (see [DATA-STEWARDSHIP.md](DATA-STEWARDSHIP.md)) · accessibility office engaged · faculty champion
identified · student representatives involved · support model agreed · success metrics agreed.

**Pilot threshold:** 30 of 50, and no item scored 1. It's the same principle as the scorecard: one missing foundation
isn't offset by the others.
