Runbooks

Owner: on-call. Status: draft, October 2026. Each runbook: detect → stabilise → fix → verify → tell people → write it down. Log every step with time in the incident record in /ops.

R1 · Bad release

  1. Confirm the error spike started with the latest deploy (deploy time vs error graph).
  2. Promote the previous Vercel deployment. If a migration ran, check it's backwards-compatible; if not, follow R4.
  3. Verify error rate back under 1% for 15 min.
  4. If a pilot is affected for more than 30 min, tell the sponsor within 1 hour.
  5. Open a fix PR with a test that reproduces the failure.

R2 · SSO outage

  1. Check the IdP status and the SAML error in logs (metadata, certificate, clock skew, attribute mapping).
  2. If the IdP is down: post on the status page, tell the institution IT contact; nothing to fix on our side.
  3. If our config: restore the last known-good SP config from the config history; never weaken signature checks.
  4. Certificate rotation: exchange new metadata with institution IT, test with a staging account first.
  5. Verify a test login per pilot role.

R3 · SIS sync stale or mismatched

  1. Open the sync run history: last success, failing step, dead-letter count.
  2. Credential or API error: check expiry with institution IT; rotate server-side only.
  3. Schema drift: pause the mapping, show the delay badge to users (freshness policy blocks consequential actions automatically), fix mapping in a new version, re-run.
  4. Mismatches: never auto-correct. List them, ask the registrar data owner which source is right, re-sync.
  5. Replay dead-letter events after the fix; confirm reconciliation shows 0 unexplained mismatches.

R4 · Backup and restore

  1. Identify the restore point (point-in-time or nightly backup ID).
  2. Restore to a new scratch project first; never overwrite production blindly.
  3. Verify row counts and a sample of records against the last reconciliation.
  4. Cut over by pointing the app at the restored database, or copy back the affected tables only.
  5. Record start and end time: that's the measured recovery time. Monthly drills follow the same steps on a scratch project.

R5 · Suspected student-data exposure

  1. Turn off the affected feature or the pilot cohort flag first.
  2. Preserve evidence: logs, audit events, the request IDs. Don't delete anything.
  3. Founder becomes incident commander. Start the incident record (S1).
  4. Assess: which records, which tenant, who could see them, for how long.
  5. Notify the institution's security contact without undue delay and within the DPA deadline; the institution decides on notices to students.
  6. Fix, add a test that proves the fix, re-run RLS suite, re-enable only after the go/no-go check.
  7. Postmortem within 5 business days, shared with the institution.

R6 · AI gateway

  1. Provider outage: switch to the fallback model if approved for the tenant, else show "Ask Semester is unavailable" with links to the official offices.
  2. Block spike: sample blocked prompts (metadata only) to check whether a UI change is sending record fields; fix the client.
  3. Cost spike: spend cap stops requests; check for loops or abuse; raise the cap only with founder approval.

R7 · Capacity

  1. Check storage, connections and compute in Supabase metrics.
  2. Clear stale projections or logs past retention.
  3. Upgrade compute size if sustained; note the cost change against the finance model.

R8 · Student can't see their data

  1. Confirm membership and role mapping for the user (IdP attributes).
  2. Check the student is in the pilot cohort and the feature flag is on.
  3. Check sync freshness for that student's records.
  4. Reply with the support macro; never paste record content into the ticket.
