# CC-1224 · Bootstrap the `platform` root and its state store

## Summary

Creates the Terraform state bucket and its scoped credential (by hand, per
`infra/bootstrap/`), then applies the `platform` root once from the
maintainer's machine. That root creates the `infrastructure-plan` and
`infrastructure-production` GitHub environments (which the pipeline's secrets
live in, so the pipeline cannot create them) and brings the repository's
protections under code: default-branch ruleset read from
`.github/rulesets/main.json`, Actions allow-list with SHA pinning, read-only
default workflow token, and reviewers on the `production` environment. Every
later change goes through `infra-apply.yml`.

## Environments and tenants affected

`platform` only (GitHub repository settings). No tenant, deploy or database
setting changes. Visible effects once applied: third-party actions outside the
allow-list stop running; a workflow without its own `permissions:` loses write
access to the repository; `production` deployments wait for a reviewer.

## Risk

A workflow that silently relied on the old default write token would start
failing. Mitigation: the plan is read before it is applied, every existing
workflow declares its own permissions (the policy checks this), and the first
red run points at the missing permission. A mistaken ruleset would block merges
to `main`; the same file already governs it today, so the plan should show no
ruleset change, and any difference is drift worth knowing about.

## Rollback

Re-run `terraform apply` in `envs/platform` from the previous commit, or
change the three settings back in GitHub → Settings (Actions → General, Rules,
Environments); nothing here holds data. The state bucket can stay: it is empty
until the first apply and costs cents. Revoke the bootstrap token after use.

## Evidence

converge plan from the `infra-apply.yml` run that follows (ACTIVATION step 4).
