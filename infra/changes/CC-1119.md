# CC-1119 · Carry the fail-closed support email-notice flag through the Pages build

## Summary

Adds `VITE_SUPPORT_EMAIL_NOTICES` to the Pages workflow environment and to the
explicit allow-list of variables carried into the production build. The app
accepts only the exact value `true`; unset or any other value remains `off`.
The server-side `SUPPORT_NOTIFY_VENDOR_APPROVED=true` check is a separate
fail-closed gate and is not enabled by this change. The current-main
`VITE_TODAY_SHADOW` and `VITE_DOMAIN_TASKS` entries remain intact.

## Environments and tenants affected

None on merge. No variable, provider approval, tenant, connector or recipient
is activated by this record. In-app support continues independently. A user can
see the per-ticket email opt-in only after a later, separately authorized build
sets the public flag to the exact value `true`, and delivery still requires the
server approval gate.

## Risk

A misspelled or omitted workflow entry could make the app disagree with the
operator's configured value. The deploy and experience-flag tests cover the
mapping, while the release console reports the built state. An unintended
activation would be visible in Help after a Pages deployment; the server would
still refuse delivery unless its separate approval gate were also enabled.

## Rollback

Unset `VITE_SUPPORT_EMAIL_NOTICES` or set it to any value other than exact
`true`, then run the guarded Pages workflow; that restores the hidden opt-in in
one deployment. Reverting the two workflow entries and the corresponding app
flag integration is the code rollback. No infrastructure state, provider
credential, tenant data or sent message must be unwound.

## Evidence

Pull request 1119. On the current-main merge tree, the focused deployment,
experience-flag, retention, scheduler, privacy, support-notification,
support-queue and release-console tests passed locally. Hosted CI, CodeQL and
HawkScan remain the authoritative merge gates for the exact head.
