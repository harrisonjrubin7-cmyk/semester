# CC-1233 · Run the supply-chain workflow on root manifest and lockfile changes, and guard where workflows install

## Summary

`supply-chain.yml` runs on a push to main that changes `app/**`, `packages/**`
or itself. Since `app/` joined the npm workspace the dependency set lives in the
root `package.json` and `package-lock.json`, so a dependency bump that touches
only those files did not trigger it, although the workflow's header says it runs
"for every change to the app's dependencies". This adds the two root files to
the path filter.

It also adds `app/src/lib/ops/workflowinstalls.test.ts`, which fails any
workflow that runs `npm ci` inside a workspace member (`app/`, `packages/*`) or
in a directory with no lockfile. `workflowpaths.test.ts` (CC-1227) resolves the
paths a workflow names, which is what stopped this workflow in `setup-node`; it
cannot see that `npm ci` in `app/` is the wrong place to install from, because
`app/` exists.

The install fix itself is not part of this change. It landed in #1227 (CC-1227)
while this pull request was open; this record was narrowed to what that change
did not cover. **Applies nothing.** No Terraform root, policy exception or
ruleset changes.

## Environments and tenants affected

None. The workflow reads the repository and writes only an attestation and a
workflow artifact. No deploy, production setting or tenant can notice.

## Risk

The wider path filter runs the workflow on every change to the root manifest or
lockfile, including dependency bumps, which is the intent: one build and
attestation per such change, visible in the Actions tab. The concurrency group
does not cancel an in-progress run, so bursts queue.

The new test could flag a future workflow that legitimately installs in a
member. It should not: every existing workflow installs from the root except
`video/`, which has its own lockfile and is recognised. If it ever fires, the
workflow is what to fix, not the test.

## Rollback

Revert the merge commit. That narrows the trigger back to `app/**`,
`packages/**` and the workflow file and removes the test. Nothing was applied,
so there is no infrastructure state to unwind. Time: one pull request.

## Evidence

On main since #1227, the `Supply chain` job has concluded `success` on pushes
(runs 32, 35 and 36), including its attest and verify steps; job conclusions
only, the logs were not opened.

The guard, shown to fail: with `working-directory: app` put back in front of
`npm ci` in the real workflow, `workflowinstalls.test.ts` fails and names
`supply-chain.yml:77`, while `workflowpaths.test.ts` passes 4 of 4 on the same
regression; restored, it passes (7 of 7). Gates run from `app/` after the
narrowing are recorded on the pull request, #1233.
